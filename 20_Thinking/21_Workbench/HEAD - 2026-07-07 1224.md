## Runbook: Auditing SpiceDB Permissions via Zed CLI on Headless Jumpboxes

This guide details how to query our SpiceDB instance from a cluster jumpbox to audit user access, verify RBAC roles, and map them to permitted operations for customer requests.

### 1. Connecting to SpiceDB

If SpiceDB is not exposed via an ingress, you must port-forward the service to your jumpbox:

Bash

```sh
kubectl port-forward svc/spicedb 50051:50051 -n <namespace> &
```

#### Bypassing Keyring Errors

When running on a headless Linux jumpbox, the `zed context set` command will likely fail with:

`error="Object does not exist at path “/”"`

This happens because the OS lacks a desktop keyring (D-Bus secret service) to store the pre-shared key. Do not use `zed context set`. Instead, export the connection details as environment variables for your session:

Bash

```sh
export ZED_ENDPOINT="localhost:50051"
export ZED_TOKEN="<your-preshared-key>"
export ZED_INSECURE="true"
```

Once these are exported, `zed` commands will authenticate automatically.

### 2. Discovering User Roles

To find out what roles a user holds within a specific tenant or project, you can dump the raw relationships and filter by their Auth0 ID.

Warning: Auth0 IDs contain a pipe character (`|`). You must wrap the ID in quotes to prevent Bash from interpreting it as a pipe command.

Find a user's roles within a specific tenant:

Bash

```sh
zed relationship read fitfile/tenant:<TENANT_ID> | grep "<AUTH0_ID>"
```

_Example Output:_

Plaintext

```sh
fitfile/tenant:0UAB5hhjH0dzhvViFF47Lal0IY5OLoup organisation_admin fitfile/user:auth0|633ad…
```

Find a user's roles across all projects:

Bash

```sh
zed relationship read fitfile/project | grep "<AUTH0_ID>"
```

### 3. Testing Caveated Access

If a user holds a caveated relationship (e.g., `results_type_access` dictating which data types they can see), a standard permission check will return `CAVEATED` instead of `TRUE`.

To verify their access, you must inject the expected context using the `--caveat-context` flag (passing valid JSON) and use `--explain` to trace the logic:

Bash

```sh
zed permission check fitfile/project:<PROJECT_ID> read_results 'fitfile/user:auth0|<AUTH0_ID>' \
  --caveat-context '{"context_result_type": "Anonymised"}' \
  --explain
```

_The `--explain` trace will show a `✓` next to the caveat logic if the context matches the user's allowed attributes._

### 4. Translating Roles to Permitted Operations

When a customer requests a breakdown of "Authorised Operations," we map the raw relations found in Step 2 back to the SpiceDB schema definitions.

For example, looking at the `fitfile/tenant` schema:

- `organisation_admin` grants:
    - `login_organisation`, `read_data_sources`, `read_data_catalogue`
    - `create_project`, `delete_project`
    - `create/read/update/delete_organisation_member`
    - `enable_data_disclosure`
    - `connect_data_partner_tenant`, `connect_data_consumer_tenant`
- `data_set_manager` grants:
    - `login_organisation`, `read_data_sources`, `read_data_catalogue`, `read_operations`
    - `create/update/delete_data_source`
    - `read/export_data_set`
    - `create/read/update/delete_data_schema`
    - `create/read/update/delete_transformation_templates`
    - `authorise_data_disclosure`
    - `write_datasource_project_connections`, `write_datasource_tenant_connections`
