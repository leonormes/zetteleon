## What is CUE and Why is it Used Here?

CUE (Configure, Unify, Execute) is an open-source data constraint language. In this project, CUE is acting as the "glue layer" between your Terraform infrastructure and your Kubernetes (Helm/ArgoCD) deployments.

Instead of writing massive, error-prone `values.yaml` files by hand, or using complex Helm Go-templates, CUE allows you to generate robust Kubernetes configuration by:

1. Guaranteeing type-safety (catching bad configurations before they are deployed).
2. Bridging dynamic values created by Terraform (like FQDNs or specific toggles) securely into the app config.
3. Standardizing all the fixed boilerplate (like vault secret mappings, monitoring standards, or registry URLs) so engineers don't have to manually re-type them for every customer.

---

## How the Pipeline Works

The entire workflow goes from Terraform $\rightarrow$ CUE $\rightarrow$ Helm values.yaml. Here is the step-by-step breakdown:

### 1. The Trigger (`make generate-values`)

The process usually kicks off via the Makefile running `scripts/generate-values.sh`. First, it grabs the output that Terraform generated in its last run:

```sh
INFRA_JSON=$(terraform output -json infra_facts | jq -c '.')
```

This JSON contains all the customer-specific parameters (like `customer_short_name`, `deployment_key`, and which app features like `spicedb` or `frontend` are toggled `true`/`false`).

### 2. Schema Validation (schema_infra.cue)

Before generating anything, CUE intercepts this Terraform JSON and validates it against the strictly defined contract inside schema_infra.cue:

```cue
InfraFacts: {
    customer_short_name: string
    deployment_key:      string
    // … toggles and settings expected from TF
}
```

If Terraform didn't output the required fields, CUE will immediately fail the build. This acts as a massive safety net.

### 3. Enforcing Platform Standards (policy_defaults.cue)

policy_defaults.cue file contains the `#PlatformPolicy` definition. This houses all the "hardcoded" platform-level defaults that shouldn't change wildly between customers, such as:

- Auth0 domains
- Default image registries (`fitfileregistry.azurecr.io`)
- Default DB versions and volume sizes
- Boilerplate cert-manager ports

### 4. The Engine Room (render_fitfile.cue)

This is where the magic happens. 

render_fitfile.cue takes the validated Terraform inputs (`infra`) and the platform defaults (`policy`), and merges them to build the final `values` tree.

It handles complex logic mapping, such as:

- Checking if a feature is enabled and inserting the right VaultSecret object (e.g. `if infra.s3_export.enabled`).
- Assembling Ingress/TLS configs automatically based on the `infra.public_fqdn`.
- Injecting Vault-to-Kubernetes secret transformation templates (like dynamically building `mongodb_connection_string` or Auth0 targets) based on the specific `customer_short_name`.

### 5. Outputting the Final YAML

Finally, the script exports the CUE object tree into a plain, validated YAML file:

bash

cue export./cue/values.cue./cue/*.cue -t "infra=$INFRA_JSON" -e values --out yaml > generated/values.yaml

This outputs a completely populated `generated/values.yaml` file, which is then usually committed to Git and ingested natively by ArgoCD.

## Mkuh-prd-4

Production infrastructure deployment repository for Milton Keynes University Hospital (MKUH), managed by FITFILE Platforms. This repo provisions and configures an Azure/AKS environment using a GitOps, data-driven pipeline.

---

### How It Works

`config/customer.yaml` is the single source of truth. Everything else—Terraform resources, Helm values, Jumpbox config—is derived from it.

```

config/customer.yaml ← Edit this to configure the customer

↓

locals.tf ← Derives all values (naming, networking, feature flags)

↓

values_generator.tf ← Assembles `infra_facts` Terraform output

↓

scripts/generate-values.sh ← Extracts output, runs CUE validation + export

↓

cue/ (schema + rendering) ← Type-safe transformation to Helm values

↓

generated/values.yaml ← Consumed by ArgoCD for Helm deployment

generated/genjump.tf ← Jumpbox Terraform (applied via jumpbox_generator.tf)

```

### Making Configuration Changes

#### Customer Configuration (`config/customer.yaml`)

Controls:

- Customer identity: `name`, `full_name`, `env`, `region`, `id`
- Network CIDR (`network.vnet_address_space`)—subnets are auto-calculated via `cidrsubnet()`
- AKS node pool sizes and autoscaling bounds
- App-level overrides: `ffcloud_admin_user_id`, `fitconnect_feature_flags`, `ffcloud_service_accounts`, `fitconnect_hosts`
- Feature flag overrides (production defaults most features on, except `seedData` and `workflowsIntegrationTests`)

After editing `customer.yaml`, run:

```bash

make generate-values

```

#### Adding a New Field to `infra_facts`

Changes are required in all four layers in order:

1. `config/customer.yaml`—add the raw value
2. `locals.tf`—derive/transform the value
3. `values_generator.tf`—expose it in the `infra_facts` output
4. `cue/schema_infra.cue`—add it to the `#InfraFacts` schema

#### Layer Ownership Rule

| Layer                 | Owns                                                          |
| --------------------- | ------------------------------------------------------------- |
| `customer.yaml`       | Customer-specific literals                                    |
| `policy_defaults.cue` | Platform-wide constants                                       |
| `locals.tf`           | Derived values only—no literals                               |
| `render_fitfile.cue`  | Mapping only—reads from `infra.*` and `policy.*`, no literals |

### Bootstrap Workflow (New Customer Only)

Only required when standing up a brand-new customer environment. For day-to-day work on MKUH, skip this section.

#### Step 1—Prerequisites

Export your GitLab token:

```bash
export GITLAB_TOKEN="your_personal_access_token"
```

Create `secrets.auto.tfvars` (gitignored) with the bootstrap credentials:

```hcl

# secrets.auto.tfvars
ude_key = "your_ude_key"
tfc_oauth_token_id = "ot-xxxxxxxxxxxxxxxxx"
tfe_token = "xxxxxxxx.xxxxxxxxxxxxxxxxx.xxxxxxxx"
vault_address = "https://your-vault-url.com"
```

> Tenant keys (`tenant_private_key`, `tenant_public_key`) are not required at this stage—they are added later during the full infrastructure apply.

#### Step 2—Configure the Customer

Edit `config/customer.yaml` with the customer identity, network CIDR, and node pool configuration.

#### Step 3—Run the Bootstrap

`make bootstrap` runs a pre-flight check first, then handles provider configuration and local state automatically. No manual edits to `providers.tf` are required.

```bash
make bootstrap
```

The pre-flight check verifies:

- All required keys are present in `secrets.auto.tfvars` with no placeholder values
- `GITLAB_TOKEN` is set and accepted by the GitLab API
- The TFC token is valid
- Vault is reachable

On success, it creates the GitLab repo, TFC workspace, Vault namespace, and KV mount using local state.

#### Step 4—Migrate State to Terraform Cloud

```bash
make finish-bootstrap
```

Re-enables the remote backend, migrates local state to TFC (you'll be prompted to confirm), and prints the `git` commands needed to push to the new GitLab repo.

Once pushed, Terraform Cloud is fully hooked up and will plan/apply the rest of the infrastructure automatically.

> Recovery: if `finish-bootstrap` fails after `bootstrap` has completed, it is safe to re-run—it checks for a local `terraform.tfstate` before attempting migration.
