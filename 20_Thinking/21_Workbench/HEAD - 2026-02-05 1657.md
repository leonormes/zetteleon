## What Azure Docs Support in Your Reasoning

### 1) The "routing paradox" is Real (destination-based routing)

Azure routing is destination-prefix based (longest-prefix match). It can't tell "this packet is a reply" vs "new outbound" when the destination is a public IP—routing decisions are made on the destination prefix, not connection intent. ([Microsoft Learn](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-networks-udr-overview?utm_source=chatgpt.com "Azure virtual network traffic routing"))

So if your subnet keeps normal internet egress (system 0.0.0.0/0 to Internet) and you attach a NAT Gateway, outbound-to-internet flows from that subnet will be SNATed using the NAT Gateway. ([Microsoft Learn](https://learn.microsoft.com/en-us/azure/nat-gateway/nat-overview?utm_source=chatgpt.com "What is Azure NAT Gateway? | Microsoft Learn"))

### 2) If You Force 0.0.0.0/0 to a firewall/NVA, You _bypass_ NAT Gateway

Microsoft is explicit: if you add a UDR that sends `0.0.0.0/0` to an NVA/VPN/ER gateway, traffic doesn't pass through NAT Gateway (because you've removed the subnet's default internet path NAT Gateway relies on). ([Microsoft Learn](https://learn.microsoft.com/en-us/azure/nat-gateway/faq?utm_source=chatgpt.com "Frequently asked questions for Azure NAT Gateway"))

That validates your constraint: "we can't just swing 0/0 to the firewall, because we want to keep NAT Gateway egress."

### 3) Why SNAT on Inbound DNAT "fixes" the Asymmetry

Your core idea—change the packet so the return destination is private—is exactly how you force the reply to stay inside the VNet/peering instead of following the internet path.

This is also the same fundamental reason Microsoft calls out asymmetric routing as a problem for inbound DNAT scenarios (if return traffic doesn't come back through the same stateful device, the session breaks). ([Microsoft Learn](https://learn.microsoft.com/en-us/azure/firewall/firewall-known-issues "Azure Firewall known issues and limitations | Microsoft Learn"))

## The Key Caveat: if This is Azure Firewall, SNAT May Already Be Happening

Azure Firewall has a documented behavior/limitation:

- "Inbound DNAT rules always change the source IP address for return traffic." ([Microsoft Learn](https://learn.microsoft.com/en-us/azure/firewall/firewall-known-issues "Azure Firewall known issues and limitations | Microsoft Learn"))

In other words, for Azure Firewall specifically, your "ask the network team to enable SNAT on the DNAT rule" is often not an optional knob—it's effectively how Azure Firewall behaves for inbound DNAT (and one reason people rely on `X-Forwarded-For` at higher layers).
