## Task

Fix an incorrect Grafana Alloy label-drop configuration in the FITFILE deployment repo.

## Context

Commit 450ad7fa4 (feature/extend-grafana-alloy-metrics-coverage) extended

Alloy's scraped namespace scope, which activated `kube_pod_status_reason` and

similar kube-state-metrics series carrying a high-cardinality `uid` label

(643 unique UIDs on testing alone, ~18,000 series on staging from this one

metric).

A fix was drafted to drop the `uid` label but used the wrong Alloy component.

It specified `discovery.relabel`, which operates at discovery time (filtering

which targets get scraped)—not the right tool for dropping a label already

present on a scraped metric.

## File

charts/ffnode/templates/_grafana.tpl

## What to Change

Add a `kube-state-metrics.extraMetricProcessingRules` block, mirroring the

existing cAdvisor pattern already in this file (~line 188-195):

cadvisor: metricsTuning: useDefaultAllowList: true extraMetricProcessingRules: | // Drop `id` and `container_id` labels from all cAdvisor metrics. rule { regex = "(id|container_id)" action = "labeldrop" }

Apply the same pattern to the `kube-state-metrics:` block (~line 182-187),

adding an `extraMetricProcessingRules` entry that drops the `uid` label:

rule { regex = "uid" action = "labeldrop" }

## Constraints

- Only touch the `kube-state-metrics:` block. Do not modify the
  `serviceMonitors.namespaces` list, `annotationAutodiscovery`, or the
  cAdvisor block.
- Match existing comment style (see cAdvisor block for the format).
- Do not change any other file.

## Verification (Mirror the oRiginal cOmmit's oWn vErification mEthod)

Run and report output:

make render-manifests DEPLOYMENT=fitfile/testing

Confirm the rendered Alloy config shows the new `extraMetricProcessingRules`

rule under kube-state-metrics, with no unrelated diffs elsewhere in the file.
