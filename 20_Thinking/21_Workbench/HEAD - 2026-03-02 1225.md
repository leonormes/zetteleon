Configuring Node Exporter Security Context

  In the FITFILE monitoring stack, Node Exporter is deployed as a sub-dependency of the clusterMetrics feature. If your cluster has strict Pod Security Policies (PSP) or Admission Controllers (like Kyverno or Gatekeeper), you

  may need to override the default security settings to resolve "disallowed" errors.

  Configuration Path

  Because of the chart's hierarchical structure, the overrides must be placed under the clusterMetrics.node-exporter key in your root values.yaml.

   - Root Chart: k8s-monitoring
   - Feature Alias: clusterMetrics (points to feature-cluster-metrics)
   - Component Alias: node-exporter (points to prometheus-node-exporter)

  YAML Configuration Example

  Add or update the following block in your values.yaml file:

    1 clusterMetrics:
    2   node-exporter:
    3     # 1. Pod-level Security Context
    4     # Applied to the entire Pod
    5     securityContext:
    6       fsGroup: 65534
    7       runAsGroup: 65534
    8       runAsNonRoot: true
    9       runAsUser: 65534

   10 # seccompProfile:

   11 #   type: RuntimeDefault

   12

   13 # 2. Main Container Security Context

   14 # Applied specifically to the node-exporter container

   15 containerSecurityContext:

   16 readOnlyRootFilesystem: true

   17 allowPrivilegeEscalation: false

   18 capabilities:

   19 add:

   20 - SYS_TIME # Required if gathering clock-related metrics

   21 drop:

   22 - ALL

   23

   24 # 3. RBAC Proxy Security Context (if enabled)

   25 # Applied to the sidecar that protects the metrics endpoint

   26 kubeRBACProxy:

   27 containerSecurityContext:

   28 allowPrivilegeEscalation: false

   29 capabilities:

   30 drop:

   31 - ALL

   32 readOnlyRootFilesystem: true

   33 runAsNonRoot: true

   34 runAsUser: 65532

  Common Security Fixes

  ┌────────────────────────────────────────┬────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────┐

  │ Issue │ Solution │

  ├────────────────────────────────────────┼────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────┤

  │ Privileged container not allowed │ Set allowPrivilegeEscalation: false in containerSecurityContext. │

  │ Must run as non-root │ Set runAsNonRoot: true and provide a numeric runAsUser (e.g., 65534). │

  │ Read-only root filesystem required │ Set readOnlyRootFilesystem: true. Node Exporter uses host mounts for data, so the container's own root can usually be read-only. │

  │ Capabilities "ALL" disallowed │ Use the capabilities.drop: ["ALL"] block shown above. │

  └────────────────────────────────────────┴────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────┘

  OpenShift Considerations

  If you are deploying to OpenShift, the cluster typically manages UIDs automatically via Security Context Constraints (SCC). In this case, you may need to omit the runAsUser and fsGroup fields to allow the platform to assign

  them:

   1 clusterMetrics:

   2 node-exporter:

   3 securityContext:

   4 runAsNonRoot: true # Still required, but let SCC handle the specific ID

   5 containerSecurityContext:

   6 allowPrivilegeEscalation: false

  Verification

  After applying the changes, verify the Pod's effective security context using kubectl:

   1 kubectl get pod -l app.kubernetes.io/name=node-exporter -o jsonpath='{.items[0].spec.containers[0].securityContext}'
