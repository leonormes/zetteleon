### Part A—Config Defects Found (Not in the tIcket, fIxable tOday)

I ran the official `renovate-config-validator` (v43.288.0) against `renovate-config/default.json`. It fails. These options survive config migration and are then silently dropped:

|Option|Where|Consequence|
|---|---|---|
|`registries`|packageRules[0] (migrated from `docker.registries`)|The ACR registry `fitfileregistry.azurecr.io` is not configured at all. Should be `registryAliases` or a `hostRules` entry.|
|`excludePaths`|packageRules[6], [7]|The `/FITFILEPublic/` and `/Fitfileregistry/` Dockerfile exclusions do nothing. Not valid inside `packageRules`—only top-level.|
|`retryCount`|packageRules[2]–[7]|No such Renovate option. Six no-ops.|
|`helm: {enabled: true}`|top level|No such option (managers are `helmv3`/`helm-values`/`helmfile`). Inert—helm is on by default anyway.|
|`commitMessage` (×6)|packageRules|Deprecated; also overrides `commitMessagePrefix` wholesale. Currently benign (the string contains `FFAPP-9000`) but it's a push-rule landmine if anyone edits it.|

Separately, validating `default.json` as a repo config (which is what it is—every repo consumes it via `extends`) produces:

```
The "repositories" option is a global option reserved only for Renovate's
global configuration and cannot be configured within a repository's config file.
```

…same for `binarySource`, `onboarding`, `onboardingCommitMessage`.

This is significant. The `repositories` array in [default.json:4-10](https://claude.ai/renovate-config/default.json) is dead config. The only thing that actually controls scope is `autodiscoverFilter` in [renovate-runner/config.js:58-63](https://claude.ai/renovate-runner/config.js). The two lists have already drifted (`default.json` still lists `terraform-infrastructure/tfc-modules/*`, which config.js deliberately removed), and the comments in config.js show real effort spent keeping them in sync—only one of them has ever done anything.

Also worth knowing: `hostRules[].password: "{{ env.DOCKER_REGISTRY_PASSWORD }}"` only resolves if `exposeAllEnv` or `allowedEnv` is set in the _global_ config. Neither is set in `renovate-runner/config.js`. Combined with the dropped `registries`, private ACR image lookups are almost certainly not working.

### Part B—The Eight Ticket Items

#### 1. Merge Train serialisation—confirmed, Architectural, One Cheap Mitigation

Confirmed in the deployment repo: [`staging.gitlab-ci.yml`](https://claude.ai/Deployment/deployment/staging.gitlab-ci.yml) has `resource_group: staging` on three jobs (`prepare_kube_config:17`, `sync_argo_app:42`, `run_integration_tests:61`), and the parent `trigger_integration_tests` in [staging-pipelines.yml:42](https://claude.ai/epitaxy/deployment/pipeline/staging-pipelines.yml:42) holds `resource_group: deployment-repo`. Every train member serialises through all four.

The root cause is one shared `testing` ArgoCD environment—that's a real project, not a config tweak. But there's a cheap win first:

GitLab resource groups default to `process_mode: unordered`, which grants the lock to whichever job is ready—so a _newer_ train pipeline can jump ahead of the train head and starve it. `oldest_first` matches merge-train ordering.

```bash
curl --request PUT --header "PRIVATE-TOKEN: $TOKEN" \
  --data "process_mode=oldest_first" \
  --url "https://gitlab.com/api/v4/projects/<deployment-project-id>/resource_groups/staging"
```

Caveat from the docs: don't use `oldest_first` when a _child_ pipeline needs the _same_ resource group as its parent—deadlock. Here the groups differ (`deployment-repo` in InsightFILE, `staging` in deployment), so this is safe. Check the current mode with `GET` on the same URL before changing it.

#### 2. Security Patches Jumping major—mostly Working as Designed, but Cappable

`vulnerabilityAlerts.vulnerabilityFixStrategy` already defaults to `"lowest"` ("propose the earliest version with a fix"). So when a security MR jumps a major, that major genuinely _is_ the lowest non-vulnerable release. Not a bug.

If you want a cap anyway, `isVulnerabilityAlert` is exposed on the config object, so `matchJsonata` can target security PRs specifically:

```json
{
  "matchJsonata": ["isVulnerabilityAlert = true"],
  "matchUpdateTypes": ["major"],
  "dependencyDashboardApproval": true
}
```

That routes major security fixes to the Dependency Dashboard for a human tick instead of auto-raising an MR—the vulnerability stays visible, it just doesn't land unattended.

#### 3. PR granularity—the Middle Ground Should Mirror CI Coverage

There is no "max N deps per PR" option in Renovate; I checked the full option list. The available lever is `matchFileNames`, and the right boundary to cut on is which CI jobs verify the change. Replace the single `"Patch Updates"` group with four:

```json
{ "matchUpdateTypes": ["patch"], "matchFileNames": ["apps/frontend/"],
  "groupName": "Patch: frontend", "branchPrefix": "bugfix/patch-fe-" },
{ "matchUpdateTypes": ["patch"],
  "matchFileNames": ["apps/ffcloud/","apps/fitconnect/","apps/scheduler-service/","packages/"],
  "groupName": "Patch: backend services", "branchPrefix": "bugfix/patch-be-" },
{ "matchUpdateTypes": ["patch"], "matchFileNames": ["apps/tasks/","apps/workflows-api/"],
  "groupName": "Patch: python tasks", "branchPrefix": "bugfix/patch-py-" },
{ "matchUpdateTypes": ["patch"], "matchManagers": ["dockerfile","gitlabci"],
  "groupName": "Patch: images", "branchPrefix": "bugfix/patch-img-" }
```

Every group then maps onto a known set of verification jobs, which is the property you actually want—not just "fewer PRs".

#### 4. Base Image bumps—better than Feared, with Two Real Holes

I ran Renovate's actual extractors over the repo. Good news:

- `apps/tasks/nhs-pet/Dockerfile`'s `ARG PYTHON_VERSION=3.13` → resolved correctly to `python:3.13-alpine`.
- The `gitlabci` manager does see `image: python:3.13-bullseye` in [verification-pipelines.yml:185](https://claude.ai/epitaxy/deployment/pipeline/verification-pipelines.yml:185).
- Both extract as `depName=python`, so they share a branch name and do update in one MR. Same for `node` across Dockerfiles + `engines.node` + `volta`.

The two holes:

(a) Hardcoded interpreter in job scripts. [verification-pipelines.yml:191-197](https://claude.ai/epitaxy/deployment/pipeline/verification-pipelines.yml:191) runs `python3.13 -m ensurepip`, `python3.13 -m pip install`, and `poetry==1.4.2`. No manager touches shell script bodies. When Renovate bumps that job's image to `python:3.14-bullseye`, the script still calls `python3.13` and the job breaks. Fix: use `python3` in the script (the image guarantees the version), and add a `customManagers` regex for the pinned `poetry==` version.

(b) `fitfile/sonar-nodejs:1.0.0` is Renovate-managed but repo-built. Extracted as a Docker Hub dep in 4 places, yet the tag is hardcoded in `docker build -t fitfile/sonar-nodejs:1.0.0` at [.gitlab-ci.yml:38](https://claude.ai/epitaxy/local_2e12fd32-b03d-43a0-9e09-428124df4dce). If a newer tag ever appears, Renovate will point CI at an image this repo never builds. Add to `ignoreDeps`.

Minor: `alpine`, `nginx`, `docker:latest`, `bash:latest`, `fitfile/gapv:latest` extract with no usable version—unmanageable until pinned or `pinDigests` is enabled.

#### 5. MRs Merging with no pipeline—confirmed, with an Exact Mechanism

`nhs-pet` is a Poetry/Python app (`pyproject.toml` + `poetry.lock`), not a yarn workspace. I traced every `changes:` rule for a change confined to `apps/tasks/nhs-pet/`:

- every `verify_*` job—no path match (there is no job for `apps/tasks/*` Python at all; only `apps/workflows-api` has one)
- `install_dependencies` / `audit_dependencies`—gated on `yarn.lock`, which a Poetry change doesn't touch
- `build_nhs_pet`—[build-pipelines.yml:498-503](https://claude.ai/epitaxy/deployment/pipeline/build-pipelines.yml:478) only runs on `merge_train` or release
- `trigger_integration_tests`—`merge_train` only

Zero jobs → GitLab creates no pipeline. GitLab's docs are explicit: _"A merge request with no pipelines at all is not considered to have a successful pipeline, and cannot merge"_—when "Pipelines must succeed" is enabled. Since these MRs did merge, that project setting is off. Two fixes, both needed:

1. Turn on Settings → Merge requests → Pipelines must succeed on InsightFILE.
2. Add verification jobs for the uncovered packages. The gap list: `nhs-pet`, `emis-processing`, `medcat-annotation`, `default-exit-handler`, `mutating-proxy-webhook`, `set_intersection_estimator`, `sftp-loader`, `omop_examples`—every one has a `poetry.lock`, none has a test job.

#### 6. `@types/*` lockstep—confirmed Drift, no Automatic Pairing

Renovate pairs `@types/*` with parents only for curated cases. `config:recommended` → `group:recommended` gives you `group:jestPlusTypes` and `group:react`—that's it. Everything else (`@types/lodash`, `@types/node`, `@types/koa__cors`, `@types/swagger-jsdoc`) can drift freely.

Two options: `group:definitelyTyped` (all `@types` in one PR—cuts noise, doesn't give lockstep), or explicit pairs where drift actually hurts:

```json
{ "matchPackageNames": ["lodash", "@types/lodash"], "groupName": "lodash" }
```

Note `@types/node` should be pinned to the Node major, not floated—it's `^22.0.0` today against `engines.node: 22.13.1`, which is correct; keep it that way with `allowedVersions: "<23"`.

#### 7. Grouped Patch MRs Still Hitting Lockfile conflicts—I Think I Have the Root Cause

`:rebaseStalePrs` is already extended, so `rebaseWhen: "behind-base-branch"` is global—Renovate _should_ regenerate the lockfile every time `development` moves. `updateNotScheduled` also defaults to `true`, so rebasing existing branches is _not_ blocked by `schedule: ["before 6am"]`.

But Renovate can only rebase when the runner actually executes, and [renovate-runner/.gitlab-ci.yml:73-74](https://claude.ai/renovate-runner/.gitlab-ci.yml:70) has `only: - schedules`. So the rebase cadence equals the GitLab pipeline schedule frequency. If that's daily, every merge train that lands breaks every other open Renovate MR's lockfile for up to 24 hours—exactly the symptom.

Fix: raise the GitLab pipeline schedule frequency on `renovate-runner` (hourly), and _keep_ `schedule: ["before 6am"]` in the Renovate config. New branches stay confined to the morning window; existing branches get rebased hourly. This is the single highest-leverage change on the list and it costs one dropdown.

I can't see the current schedule frequency from here—worth checking first.

#### 8. Transitive deps—the Ticket's Premise is Slightly Off, and There's a Live Footgun

`resolutions` is configured ([package.json:83-94](https://claude.ai/epitaxy/local_2e12fd32-b03d-43a0-9e09-428124df4dce)) and I verified all ten entries are Renovate-manageable (including the path-scoped `@storybook/builder-webpack5/webpack` and the `semver@npm:^7.0.0` descriptor form). Renovate maintains them fine.

The actual gap is that nothing _adds_ a resolution for a newly-found vulnerable transitive. Your `undici` example: `yarn.lock:37746` still has `undici@npm:^4.0.0` pulled in by `fastify-reply-from@^6.4.1`, alongside `^7.28.0`. Fix is a one-liner—add `"undici": "^7.28.0"` to `resolutions`—plus a documented habit of doing that whenever OSV flags a transitive.

The footgun: `.yarnrc.yml` suppresses advisories 1113041/1113042 with the comment _"webpack >=5.104.1 breaks Storybook/Next bundled webpack"_, and `resolutions` pins webpack to `5.79.0`. But `npmAuditIgnoreAdvisories` is a _yarn_ setting—it has zero effect on Renovate, which uses OSV. With `osvVulnerabilityAlerts: true`, Renovate will raise a security MR bumping webpack to exactly the version you've deliberately pinned away from. Given the branch you're on is `bugfix/FFAPP-9000-fix-webpack-resolver-types`, this seems worth pre-empting:

```json
{ "matchDepTypes": ["resolutions"], "matchDepNames": ["webpack"],
  "allowedVersions": "<5.104.1",
  "description": "Storybook/Next bundled webpack breaks on >=5.104.1 - see .yarnrc.yml npmAuditIgnoreAdvisories" }
```
