Good news and bad news. `pod` has values (e.g. `compliance-snapshotter-67cbbdbbbf-n8x58`) — but it's **not a stream label**. The `search_label_names` returned 11 labels and `pod` is absent from that list. It's landing in structured metadata instead.  

The culprit is the `structuredMetadata` block from the previous fix. You have both:  

```yaml  
labelsToKeep:  
  - pod          # tries to keep pod as a stream label  
structuredMetadata:  
  k8s.pod.name: pod   # ← this wins and pushes pod into structured metadata  
```  

When `k8s.pod.name: pod` is in `structuredMetadata`, the chart writes `pod` as structured metadata — that overrides `labelsToKeep`. **Remove the `k8s.pod.name: pod` entry entirely:**  

```yaml  
podLogs:  
  enabled: true  
  labelsToKeep:  
    - pod  
    - namespace  
    - container  
    - job  
    - node  
    - app_kubernetes_io_name  
  structuredMetadata:  
    service.instance.id: service.instance.id  
    # Remove: k8s.pod.name: pod  
```  

After applying, restart the Alloy pods and check with:  
```logql  
{cluster="testing", pod=~".+"}  
```  

The stream label list currently present is: `app_kubernetes_io_name`, `cluster`, `container`, `job`, `k8s_cluster_name`, `namespace`, `node` — so all others from the previous fix are working correctly. Only `pod` is misrouted.

This means metrics collection is currently broken. These errors point to incorrect raw Alloy syntax — likely from an `extraConfig` or `extraMetricRelabelRules` block in your `values.yaml` that was accidentally edited. In Alloy:  
- There's no standalone `keep` component — use `rule { action = "keep" … }` inside `prometheus.relabel`  
- `prometheus.scrape` uses `forward_to`, not `relabel`  

**Check your `values.yaml`** for any `clusterMetrics.extraConfig` or `extraRelabelRules` sections you may have touched. The `podLogs` change shouldn't have affected metrics config — so something else was modified.
