## Deep-Dive Report: 500K Stress Test Run—sandbox-testing-2

Run: `500k_patients-single_source-privacy_off-1` · 10:56:42 → 12:17:24 UTC · 80.7 min total · 0 failures

### Headline Finding

One step—the `measurement` table extraction—consumed 76.0 of the 80.7 minutes (94% of total wall-clock time). Everything else in the workflow (7 other table extracts, OHDSI query building, finalization) fits inside a 29-minute window that runs almost entirely in parallel with it. The system isn't slow because of a bottleneck in scheduling, contention, or failure—it's architecturally bound by the throughput of a single serial code path once one table dominates the row count.

### What the Measurement Extraction Actually Did

- Query: cohort-filtered extract from `cdm.measurement` (CTE-based `Codesets` temp table join), streamed row-by-row into a Parquet sink by the fitconnect Node.js pipeline.
- Final count: 114,300,000 rows—matches the 114,154,298 I measured directly against the DB for this exact cohort in FTFL-721 to within 0.13%, confirming the harness and my earlier sizing analysis agree.
- Throughput was dead flat: 26,021 rows/sec sustained for the entire 73.2-minute extraction phase, then 159s to save/upload the resulting artifact to MinIO. No slowdown, no degradation curve, no GC thrashing—this rules out a query-plan cliff or memory-pressure explanation.

This is the most important operational finding: during the 47-minute solo tail, the database is essentially idle while the measurement extraction runs. The bottleneck isn't SQL execution, network fetch, or DB contention—it's the client-side pipeline (schema validation + per-row Parquet serialization in the fitconnect Node.js process) pegged at roughly one CPU core the whole time. The autoscaler did exactly the right thing (scaled up for the parallel burst, back down once the small extracts finished)—this isn't a capacity problem, it's a single-threaded-per-row-throughput ceiling.

### What This Tells Us about the System

1. No failures, no resource starvation, no scheduling issues—the harness, autoscaler, and DB all behaved correctly under load.
2. Runtime is completely dominated by the largest table's row count, not cohort complexity or query planning. The 7 other extraction branches are noise against measurement's 76 minutes.
3. The real lever for making large-cohort runs faster is the per-row extraction/serialization pipeline, not more compute—the DB has massive headroom (0.12 cores idle) while the app pod sits at ~1 core the whole time. Candidates worth investigating: chunking the measurement extract into parallel range-partitioned sub-queries, increasing Parquet writer batch size, or profiling the Node.js hot path for per-row overhead.
4. Scaling behavior 100k→500k was sub-linear (32 min → 81 min for 5x the patients—2.5x the time), consistent with the DAG's parallel structure diluting the per-table serial cost somewhat. Worth watching whether that holds or inverts for the 1M run, since measurement will dominate even more heavily there.
