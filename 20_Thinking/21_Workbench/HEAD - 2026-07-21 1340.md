## Fix: Linkage-node Failure under Multi-tenant Stress Load (FFCloud)

### Context

The sandbox-testing-1 stress-testing tool ran an OMOP workflow across 5 datasources/tenants (100k patients, privacy off). It coordinated 96 sub-tasks across 5 tenants successfully for ~42 minutes, then failed on its final step—the "linkage" node, which depends on all 5 per-tenant extraction branches. Root cause, confirmed via FFCloud's own service logs in Grafana Loki:

```
Request to tenant "…" failed url="…/data-pipeline/workflows/submit" code=ERR_CANCELED
Error: canceled
    at Timeout._onTimeout (…/DistributedWorkflowSupervisor.js:130)
    at AbortController.abort (…)
```

A comparable submit call to a different tenant succeeded fine 8.3s later, so tenants aren't broken—this is a timing/load issue under this stress test's coordination overhead.

Root cause chain (`apps/ffcloud/src`):

- `services/workflows/supervisor/constants.ts:3`—`REQUEST_TIMEOUT_MS = 15000` is shared by three different call sites with very different risk profiles:
  1. `services/tenant/registry/TenantGatewayRegistrySingleton.ts:52`—axios instance's own built-in `timeout`, paired with `axios-retry` (3 retries, exponential backoff, `post` included).
  2. `DistributedWorkflowSupervisor.ts:165` (`submitOne`)—a manual `AbortController` wrapping the non-idempotent `submit` call.
  3. `DistributedWorkflowSupervisor.ts:254` (`pollOnce`)—the same pattern wrapping the idempotent, safely-retryable poll call.
- When the manual `AbortController` fires, axios throws `ERR_CANCELED`—deliberately excluded from retry in _two_ places: `packages/service-common/…/retry.ts`'s `isHttpErrorRetryable` (used by axios-retry) and `TenantConnectionRegistryError.ts`'s `isTenantGatewayNetworkError` (used by the supervisor's own catch block). The latter has an explicit comment: retrying a cancelled submit is unsafe because the tenant may have already received and started processing it. This is confirmed, intentional, tested behavior (`DistributedWorkflowSupervisor.test.ts:515`), not a bug to remove.
- The actual problem: this deliberately non-retryable, permanent-failure-on-timeout path shares its 15s deadline with the freely-retryable poll path and the generic axios default. Under this stress test's load (5 tenants, 96 tasks, heavy concurrent MongoDB writes we separately observed), 15s was tight enough that one submit got cut off before the tenant responded—permanently failing the whole 42-minute workflow on its last node.
- Critical subtlety: axios's own instance-level `timeout` (also 15s, item 1 above) races the manual `AbortController` independently. If we only raise the `AbortController`'s deadline without also disabling axios's own per-request timeout for this call, axios's shorter timeout would fire first instead, throwing the _retryable_ `ECONNABORTED`—causing axios-retry to silently, automatically retry the non-idempotent submit 3×. That reintroduces the exact duplicate-submission risk the current design avoids. Both timers must move together.

### Recommended Changes

Scope: give the non-idempotent submit path more headroom before giving up, make that headroom configurable per environment, and add observability—without touching the existing non-idempotency safety guard.

1. `apps/ffcloud/src/config/config-types.ts`—add to `configSchema`, next to `exchangeTimeoutMs`/`dataAccessApprovalTimeoutMs`:

   ```ts
   submitRequestTimeoutMs: z.number().positive(),
   ```

2. `apps/ffcloud/src/config/default.ts`—add, with a comment explaining why it must exceed the poll timeout:

   ```ts
   // Deliberately > REQUEST_TIMEOUT_MS (poll). Non-idempotent workflow "submit" calls are never
   // safely retryable on timeout (see isTenantGatewayNetworkError's doc comment), so give them
   // more headroom than the freely-retryable poll path before treating a slow tenant response
   // as a permanent node failure.
   submitRequestTimeoutMs: 45_000,
   ```

   (45s is a starting judgment call—comfortable margin over the ~15-25s range implied by the incident. Confirm with the team before shipping; easy to retune later since it's now config, not a redeploy.)

3. `apps/ffcloud/src/services/workflows/supervisor/DistributedWorkflowInstanceAdapter.ts` (`submit()`, ~line 79-83)—required companion change, not optional: pass `timeout: 0` in the request config to disable axios's own per-request timeout for this call, so the manual `AbortController` (below) is the _sole_ authority on the submit deadline:

   ```ts
   const res = await tenantGateway.post<OperationTrackingDTO>(
       path,
       { task_signatures, workflow_payload, sender_details },
       { signal, xApi: true, timeout: 0 },
   );
   ```

4. `apps/ffcloud/src/services/workflows/supervisor/DistributedWorkflowSupervisor.ts`
   - Add `import { config } from '@config';`.
   - Line 165 (`submitOne`): `setTimeout(() => ac.abort(), REQUEST_TIMEOUT_MS)` → `setTimeout(() => ac.abort(), config.submitRequestTimeoutMs)`.
   - Line 254 (`pollOnce`): leave untouched—still uses `REQUEST_TIMEOUT_MS`; poll failures already just back off and reschedule, never `failNode` on timeout.
   - `REQUEST_TIMEOUT_MS` stays imported from `./constants` (still used by `pollOnce`).
   - In the `else` branch (~lines 184-190), add one field to the existing `logger.warn` call: `ambiguous_submit_cancellation: isAmbiguousSubmitCancellation(e)`.

5. `apps/ffcloud/src/services/tenant/registry/TenantConnectionRegistryError.ts`—add a sibling helper to `isTenantGatewayNetworkError`, observability-only (does not change retry behavior):

   ```ts
   /
    * True when a TenantGateway call failed because our own AbortController fired before a
    * response was received (ERR_CANCELED) — i.e. we cannot tell whether the tenant received or
    * processed the request. For observability/alerting only; does not affect retry behavior.
    */
   export function isAmbiguousSubmitCancellation(e: unknown): boolean {
       if (!(e instanceof TenantConnectionRegistryError)) return false;
       const cause = (e as { cause?: unknown }).cause;
       return isAxiosError(cause) && cause.code === 'ERR_CANCELED';
   }
   ```

6. `apps/ffcloud/src/services/workflows/supervisor/__tests__/DistributedWorkflowSupervisor.test.ts`
   - Existing `SUBMIT_CONCURRENCY`/`MAX_CONCURRENCY` tests and the `'submitOne treats ERR_CANCELED as a definitive failure…'` test (line 515) need no changes—behavior is unchanged, only the deadline value/source moves.
   - Add: a test confirming `submitOne`'s abort deadline comes from `config.submitRequestTimeoutMs`, not `REQUEST_TIMEOUT_MS` (fake timers + a never-resolving `adapter.submit`).
   - Add: a test confirming `ambiguous_submit_cancellation` is `true` for the `ERR_CANCELED` case and falsy for a plain non-network failure.

7. `apps/ffcloud/src/services/workflows/supervisor/__tests__/DistributedWorkflowInstanceAdapter.test.ts` (~line 238)—add `expect(optionsArg.timeout).toBe(0)` alongside the existing `toMatchObject({ signal, xApi: true })` assertion, so the "no instance-level timeout on submit" behavior is explicitly locked in rather than incidentally passing.

### Deferred / Follow-up (Not part of tHis fIx)

- Safe retry via reconciliation: use the `task_signatures` already sent in the submit payload as an idempotency key to query the tenant ("did you already receive this?") before deciding retry-vs-fail on `ERR_CANCELED`. This is the structurally complete fix, but the FITConnect API contract lives outside this repo and needs sign-off from whoever owns the tenant side. Do not build until scoped separately.
- `SUBMIT_CONCURRENCY` configurability—same `@config` pattern would apply cleanly if larger stress runs (500k/1M cohorts) need tuning later, but there's no evidence it's the proximate cause here.
- Other `tenantGateway.post(…)` call sites with similar unprotected 15s exposure but no explicit non-retry guard at all (e.g. `DistributedWorkflowSubmitUseCase.ts`, `DeleteQueryPlanService.ts`, `DeleteUserflowService.ts`, `ResultDatasetRepo.ts`)—worth a separate audit, out of scope here.
