## 1. Introduction and Overview

This Software Design Document (SDD) serves as a technical blueprint and health assessment for the FITFILE CI/CD Pipeline ecosystem. Currently bridging code generation to deployment across multiple repositories (including `InsightFILE`, `deployment`, and `workflows-api`), the pipeline is the critical conduit for delivering value to staging and production clusters.

### Goals and Project Scope

- Document Current State: Clearly define the 7-phase lifecycle of a developer commit traversing through GitLab CI, Azure Container Registry (ACR), ArgoCD, and into an AKS cluster.
- Assess System Health: Surface critical bottlenecks, systemic failures (e.g., 100% failure rate on recent pipelines), and architectural drift causing deployment delays.
- Define Remediation Roadmap: Establish a prioritized tier-based action plan to stabilize the pipeline, improve delivery speed, and reduce single-point-of-failure bottlenecks.

This document is intended for DevOps engineers, software developers, and engineering management to align on the technical standards and structural updates required to restore pipeline health.

## 2. System Architecture

The FITFILE pipeline leverages a hybrid Directed Acyclic Graph (DAG) and sequential stage-gated architecture across multiple repositories. The end-to-end trace from commit to staging deployment encompasses 7 distinct phases.

### The 7-Phase Delivery Chain

```text
┌─────────────────────────────────────────────────────────┐
│ 1. Developer → Feature Branch → MR Pipeline             │
│ ↓                                                       │
│ 2. Merge Train → Build + Integration Test               │
│ ↓                                                       │
│ 3. Merge to development (Development Branch Pipeline)   │
│ ↓                                                       │
│ 4. Merge to main → Release Pipeline (GAPV)              │
│ ↓                                                       │
│ 5. GAPV commits new version to deployment repo          │
│ ↓                                                       │
│ 6. ArgoCD detects drift → Syncs to AKS                  │
│ ↓                                                       │
│ 7. Staging Verification (merge trains)                  │
└─────────────────────────────────────────────────────────┘
````

### Core Repositories Involved

- `fitfile/apps/InsightFILE`: Source code and primary CI definitions.
- `fitfile/deployment`: Helm charts and ArgoCD manifests.
- `fitfile/workflows-api`: Cross-project integration.

### Design Trade-offs & Limitations

The current architecture separates the application build process from the deployment manifestation. While this GitOps pattern (via ArgoCD) provides strong auditing and rollback capabilities, it introduces latency. The three-tier deployment hop (Code commit → GitLab CI Build → ACR Push → Version Bump → Deployment Repo Update → ArgoCD Sync → AKS Deployment) creates multiple gates, adding unavoidable delay to deployments.

## 3. Data Design & Artifact Management

The pipeline relies on several critical data models, caching layers, and artifact handoffs to function effectively.

### Caching Strategy

Dependencies are cached heavily to improve execution time. The `install_dependencies` job generates `.yarn/` and `node_modules/` artifacts.

> ⚠️ Current Bottleneck: The merge train pipelines currently exclude `install_dependencies`, forcing downstream build jobs to rely on a stale fallback cache key, resulting in wasted cycles (60-90s) per job rebuilding dependency trees.

### Build Artifacts & Registries

- Docker Build Cache: Stored in ACR as `<image>:buildcache` tag utilizing containerd snapshotter layer caching.
- GAPV Artifacts: The GAPV system analyzes changed packages to compute the next semantic version, passing it via an environment file (`env.sh`).
- Dangling Artifacts: Several test jobs currently lack an `expire_in` configuration, leading to infinite accumulation in GitLab storage.

## 4. Interface and Component Design

The system components are decoupled but rely on structured interfaces (mostly API interactions, webhooks, and CLI integrations).

### External Integrations

- Azure Container Registry (ACR): Target for image pushes. _Security Note:_ Staging scripts currently use an OAuth2 password grant that echoes the token to CI logs, posing a leak risk.
- ArgoCD: App of Apps pattern listening to `fitfile/deployment`. Syncs automatically based on GAPV commits modifying Helm values.
- Azure Kubernetes Service (AKS): Runtime environment. Readiness probes gate traffic until Init containers (e.g., `yarn db:migrate:remote:up`) complete.

### Component Highlights: CI Modules

The `verify_fitconnect` module extends a base verification script, requiring sequential Yarn workspace focusing, building, linting, and testing. It currently runs sequentially (totaling ~424s), representing a prime candidate for a parallel matrix split.

## 5. Developer Workflow Design

The CI ecosystem drives the developer experience. The optimal path requires early failure detection and clear feedback loops.

### Merge Request Workflows

1. Developers open an MR targeting `development`. This triggers the verification phase.
2. Upon acceptance to the merge train, GitLab generates a "merged results" pipeline, introducing build and integration testing.
3. Review Bottlenecks: Currently, a single-owner review gate blocks merge throughput. The lack of an automated CI quality gate forces manual inspection, halting scaling and creating a systemic bottleneck.

## 6. System Health & Infrastructure Dependencies

> 🚨 Critical Health Alert: The ecosystem is currently operating with a 100% failure rate over the last 10 pipelines (e.g., MR!2307) and average build durations are inflating.

### Key Bottlenecks Identified

- ESLint Violations: New Faro SDK test files introduced strict violations blocking merge pipelines.
- Regression Test Failures: The `verify_ffcloud` test suite features genuine regression failures in `Userflow.test.ts` (snapshot expectation mismatch) and `UserflowController.test.ts` (500 Internal Server error).
- Zombie Pipelines: Several pipelines have been stuck in a "running" state for over 2 years, consuming shared SaaS runner capacity.
- Resource Constraints: The GitLab Premium subscription utilizes `saas-linux-small-amd64` runners (2 vCPU, 7.5 GB RAM). Heavy jobs like UI interactions and integrations are CPU/Memory bound and lack access to Medium runners without upgrading to Ultimate or deploying self-managed instances.
- Helm Chart Linting Void: There is no CI linting coverage for `charts/ffnode`, meaning breakages only surface during live ArgoCD syncs.
- Terraform Drift: The multi-generation infrastructure rollout (Gen1 -> Gen2 -> Gen3) is causing state conflicts and require manual `terraform import` remediations across customer clusters.

## 7. Remediation Roadmap

To restore pipeline velocity and security, the following prioritized build plan has been established:

|Tier|Action Item|Impact Target|Effort|
|---|---|---|---|
|1: Immediate|Fix `fitfile/sonar-nodejs` base image (add `make g++ python3`).|Unblocks `BUILD_COMPILE` failures.|Low|
|1: Immediate|Resolve ESLint violations in Faro test files. Cancel zombie pipelines via glab CLI.|Unblocks MR!2307; frees runner capacity.|Low|
|2: Next Sprint|Implement `changes:` path filters in `InsightFILE/.gitlab-ci.yml`.|Eliminates ~40% of unnecessary pipeline runs.|Medium|
|2: Next Sprint|Refactor build jobs into a `parallel:matrix` to collapse 15+ duplicated definitions.|Removes ~400 lines of YAML; standardizes cache and image pulls.|Medium|
|3: 4-6 Weeks|Implement an automated Merge Request quality gate (CODEOWNERS + Pipeline approvals).|Removes the single-owner review bottleneck.|High|
|3: 4-6 Weeks|Complete Generation 3 IaC migration for active customer workspaces.|Resolves Terraform state drift/collision errors.|High|
|4: Strategic|Transition to trunk-based development with feature flags.|Eliminates long-lived branch merge skew.|High|

### Configuration Adjustments

A set of immediate, zero-cost configuration fixes must be applied to the GitLab settings:

- Enable Forward Deployment (`ci_forward_deployment_enabled: true`) to prevent stale pipeline results from overwriting fresh ones.
- Enable CI Job Token Scope to secure token access across projects.
- Transition from OAuth2 password grants to ID Tokens / OIDC for Azure integrations to eliminate hardcoded service principles in CI logs.
