## FTFL-638—Missing Grafana Monitoring in Testing Cluster

### Summary

Full investigation and resolution of monitoring stack failures in the testing AKS cluster. The session covered five distinct root causes, a full chart migration from v3.7.5 to v4.1.3, and a staging cluster bug discovered as a side effect.

---

### Timeline of Issues Found and Fixed

#### 1. Alloy-metrics CrashLoopBackOff—Unquoted `keep` in Alloy Config

Symptom: `grafana-k8s-monitoring-alloy-metrics-0` stuck in CrashLoopBackOff. ArgoCD showing `grafana-k8s-monitoring` as OutOfSync/Progressing.

Root cause: The Alloy config at `/etc/alloy/config.alloy:248` contained:

```
action = keep   # unquoted — parsed as a component reference, not a string
```

In Alloy's River syntax, enum values like `keep` must be quoted strings. The chart was generating this from `clusterMetrics.kube-state-metrics.extraDiscoveryRules` in the old v3.x values, which had been inadvertently set with an unquoted value.

Fix: Removed the broken `extraDiscoveryRules` block from `ffnodes/fitfile/testing/values.yaml` under `clusterMetrics.kube-state-metrics`. Deleted the pod to clear CrashLoopBackOff exponential backoff.

---

#### 2. ArgoCD Deadlock—Stuck Operations at Stale Revisions

Symptom: Multiple instances throughout the session where the `testing` parent app had a Running operation at an old git revision, blocking new commits from being applied.

Root cause: ArgoCD's automated sync starts an operation at revision X. New commits land. The operation hits its retry limit (5) or gets stuck waiting for an unhealthy resource. ArgoCD won't start a new operation while one is Running. The fix in git is invisible to the cluster.

Fix (repeated pattern throughout session):

```bash
kubectl --context fitfile-cloud-testing-aks-cluster patch application testing \
  -n argocd --type json -p '[{"op": "remove", "path": "/operation"}]'
kubectl --context fitfile-cloud-testing-aks-cluster annotate application testing \
  -n argocd argocd.argoproj.io/refresh=hard --overwrite
```

After termination, the automated sync picks up HEAD and re-evaluates.

---

#### 3. Node-exporter DaemonSet CrashLoopBackOff—Duplicate `--web.listen-address`

Symptom: All 3 node-exporter pods crashing with `listen tcp:9101: bind: address already in use`.

Root cause: The DaemonSet spec contained two conflicting listen-address flags:

```
--web.listen-address=[$HOST_IP]:9101   # auto-generated by chart (HOST_IP=0.0.0.0)
--web.listen-address=:9101               # from extraArgs in values
```

With `hostNetwork: true`, both resolve to `0.0.0.0:9101`—a self-conflict within the same container. The chart sets `HOST_IP=0.0.0.0` when `hostNetwork: true`.

Fix (v3.x): Removed `hostNetwork: true` and `extraArgs: [--web.listen-address=:9101]` from `clusterMetrics.node-exporter` in the testing values. Single listen address, no host port conflict.

Fix (v4.x, later): Set `telemetryServices.node-exporter.hostNetwork: false` to override the prometheus-node-exporter subchart default of `hostNetwork: true`. Without hostNetwork, the container uses its own network namespace—no host port binding at all.

---

#### 4. Chart Migration—v3.7.5 → V4.1.3 Breaking Changes

Context: Testing cluster was chosen as the first to upgrade to k8s-monitoring v4.x. The base ffnode chart still targets older chart versions for all other clusters.

Breaking changes hit during migration (in order):

| Error | Cause | Fix |
|---|---|---|
| `/destinations: got array, want object` | v4.x changed destinations from array to map | Convert `- name: prometheus` → `prometheus:` (remove list items, promote name to key) |
| `At least one collector should be enabled` | v4.x uses `collectors:` map; old `alloy-metrics/logs/singleton` keys removed; `alloy: null` also disabled collectors | Remove `alloy: null`; replace `alloy-metrics/logs/singleton` with `collectors:` map |
| `Pod Logs feature requires Alloy to mount /var/log` | New v4.x validation requiring filesystem preset | Add `presets: [filesystem-log-reader]` to `collectors.alloy-logs` |
| `OpenCost default cluster id should match cluster name` | New v4.x validation | Add `telemetryServices.opencost.opencost.exporter.defaultClusterId: testing` |
| `OpenCost requires linking to a Prometheus data source` | New v4.x validation | Add `telemetryServices.opencost.metricsSource: prometheus` |
| `OpenCost requires a url to a Prometheus data source` | New v4.x validation | Add `telemetryServices.opencost.opencost.prometheus.external.url` |
| `hostNetwork: true` on node-exporter DaemonSet | prometheus-node-exporter subchart defaults to `hostNetwork: true` | Override with `telemetryServices.node-exporter.hostNetwork: false` |

Full v4.x architecture changes:

| v3.x | v4.x |
|---|---|
| `destinations:` (array) | `destinations:` (object/map) |
| `alloy-metrics:`, `alloy-logs:`, `alloy-singleton:` | `collectors: { alloy-metrics: {controller: {type: statefulset}}, alloy-logs: {controller: {type: daemonset}}, alloy-events: {controller: {type: deployment}} }` |
| `podLogs:` | `podLogsViaLoki:` (with `destinations` and `collector` refs) |
| kube-state-metrics/node-exporter embedded in clusterMetrics | `telemetryServices: { kube-state-metrics: {deploy: true}, node-exporter: {deploy: true} }` |
| `opencost:` top-level | `telemetryServices.opencost:` + `costMetrics:` feature |
| `labelsToKeep:` in podLogs | Removed entirely—all discovery labels pass through |
| No `hostMetrics` feature | `hostMetrics: {enabled: true, destinations: [prometheus], collector: alloy-metrics}` |

#### 5. `pod` Missing as Loki Stream Label

Symptom: `{cluster="testing", pod="…"`} stream selectors returning no results. `pod` absent from all 207 testing cluster streams.

Root cause (v3.x): The k8s-monitoring v3.x chart hardcodes `stage.structured_metadata { values = { "pod" = "pod" } }` in the alloy-logs processing pipeline. Alloy's `stage.structured_metadata` moves labels from the stream label set to structured metadata (not a copy). The subsequent `stage.label_keep` listing `pod` is a no-op because `pod` has already been consumed.

Root cause (v4.x default): The v4.x chart also defaults `structuredMetadata: { pod: pod, k8s.pod.name: k8s.pod.name }` in `feature-pod-logs-via-loki`. However, the chart template uses `{{- if $value }}`—if the value is `null`, the entry is skipped entirely.

Fix:

```yaml
podLogsViaLoki:
  structuredMetadata:
    pod: null          # override chart default — keeps pod as stream label
    k8s.pod.name: null
    service.instance.id: service.instance.id
```

Confirmed fixed: 46/340 testing streams now have `pod` as a stream label (count growing as pods cycle through the new v4.x alloy-logs collector). Testing now has 17 stream label keys vs staging's 10.

### Staging Cluster Bug Discovered

Staging has had zero logs in Loki for 30+ days.

Root cause: The staging alloy-logs ConfigMap references `remote.kubernetes.secret.logs_service` for Loki credentials, but the `logs_service` secret does not exist in the `monitoring` namespace. The only secret present is `monitoring`. Alloy silently fails all Loki pushes with no error logged.

Fix needed (staging, separate ticket): Either recreate the `logs_service` secret with correct Loki credentials, or update the staging alloy-logs ConfigMap to reference the `monitoring` secret instead.
