Result: ✅ Viable—Bastion Direct works with the managed cluster resource ID directly.

## What Was Tested

Tested on Sandbox cluster aks-ff-uks-gp-1 (Subscription: Testing, 7bbc8ae5-1710-48ab-ab83-59b52bd0de1a).

Step 1—Open Bastion tunnel directly to the managed cluster resource:

```sh
az network bastion tunnel \
--name bas-ff-uks-gp \
--resource-group rg-ff-uks-gp-net \
--target-resource-id /subscriptions/709f3d57-b6d7-48c6-8252-6b1c1174a541/resourceGroups/rg-ff-uks-gp-net/providers/Microsoft.ContainerService/managedClusters/aks-ff-uks-gp-01 \
--resource-port 443 \
--port 8443
```

Step 2—Patch kubeconfig to route via tunnel (DNS resolution fix):

The cluster's private FQDN (*.privatelink.uksouth.azmk8s.io) does not resolve from a local machine outside the VNet. Fix: set server to 127.0.0.1:8443 and preserve the original FQDN as tls-server-name for TLS certificate validation.

```sh
`CLUSTER_NAME=$(kubectl config view --minify -o jsonpath='{.clusters[0].name}') PRIVATE_FQDN="aks-ff-uks-gp-1-ubeyrt2c.f985395b-cb31-425a-8c2e-6cea863534f0.privatelink.uksouth.azmk8s.io"  kubectl config set-cluster"$CLUSTER_NAME" --server=https://127.0.0.1:8443 kubectl config set clusters."$CLUSTER_NAME".tls-server-name "$PRIVATE_FQDN"`
```

Step 3—Verify kubectl access:

`kubectl get ns # → All namespaces listed successfully (argo, argocd, calico-system, cert-manager, etc.)`

## Key Findings

- az network bastion tunnel accepts a managedClusters resource ID directly—no need to identify the private endpoint resource ID separately.
- The tunnel itself connects successfully; the only fix required was a kubeconfig patch to route DNS via 127.0.0.1:8443 and preserve TLS SNI.
- Existing Bastion (bas-ff-uks-gp) already has the correct SKU (Standard) and flags (enableTunneling: true, enableIpConnect: true)—no infrastructure changes required.
- Authentication uses the caller's Azure AD / Entra ID identity—no SSH passwords, no jumpbox in the path.

## Recommendation

Bastion Direct is a viable replacement for the current Bastion → Jumpbox → SOCKS5 → AKS flow for interactive developer access. It eliminates:

- Password-based SSH (Prowler FAIL addressed in parent ticket FTFL-579)
- Jumpbox VM running cost
- SOCKS5 proxy complexity

Remaining concern: For CI/CD pipeline automation (ArgoCD bootstrap, Terraform), Bastion Direct is not appropriate as it requires a local az session. The TFC Agent pattern (agent inside the private VNet) remains the recommended path for pipeline-level cluster access—to be tracked separately.

Next action: Propose adoption to team; update aks-ff-up shell function to use Bastion Direct pattern. SSH key enforcement on jumpbox (FTFL-579) still required for fallback/RDP scenarios.
