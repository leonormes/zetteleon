## Investigating AKS Cluster Backups & ZRS Migration (FTFL-525)

Objective: Audit and resolve silent failures in Azure Backup for AKS long-term retention (Tiering) and convert backup storage accounts from LRS to ZRS to meet compliance requirements (10km datacentre separation).

Scope: MKUH and NNUH environments.

### Executive Summary

Operational backups (4-hourly, 7-day retention) were functioning correctly across both clusters. However, the automated copying of backup data to the Vault Store for long-term retention (12-week schedule tagged "Daily") had a 100% failure rate. The root causes were entirely distinct between the two sites, requiring separate remediation strategies.

|Site|Cluster|Storage Account|Primary Issue|Status|
|---|---|---|---|---|
|MKUH|`aks-mkuh-uks-prd-01`|`aksmkuhuksprd01bkp01`|Missing Vault MSI permissions|Resolved|
|NNUH|`aks-ff-uks-gp-01`|`aksffuksgp01backupsa`|Platform RBAC desynchronisation|Requires MS Support ticket|

### MKUH Cluster Diagnosis & Resolution

#### Symptoms & Root Cause

- Error Code: `UserErrorMissingVaultMSIPermissionsOnBackupStorageLocation`
- Diagnosis: The Azure Backup Vault's Managed Identity lacked permissions to read from the operational backup storage account.
- Impact: Effective recoverability was limited to approximately 7 days instead of the mandated 12 weeks.

#### Resolution Steps

Applied the required Role-Based Access Control (RBAC) assignment. This required escalation to a Subscription Owner/User Access Administrator due to least-privilege boundaries.

Bash

```
az role assignment create \
  --assignee-object-id <Vault-MSI-Object-ID> \
  --assignee-principal-type ServicePrincipal \
  --role "Storage Blob Data Reader" \
  --scope /subscriptions/<Sub-ID>/resourceGroups/aks-mkuh-uks-prd-01-backup-rg/providers/Microsoft.Storage/storageAccounts/aksmkuhuksprd01bkp01
```

#### Security Posture Adjustments

- Verified `AllowBlobPublicAccess` was natively `False`.
- Disabled shared key access (`AllowSharedKeyAccess: false`), forcing AAD-only authentication.
- Added the Vault MSI resource instance rule to the storage account firewall to ensure tiering will not break when the public network access is eventually disabled in favour of the existing private endpoint.

### NNUH Cluster Diagnosis & Escalation

#### Symptoms & Root Cause

- Error Code: `UserErrorMissingVaultMSIPermissionsOnSnashotRG` _(Note: Microsoft typo retained for searchability)_
- Diagnosis: Ad-hoc Tiering jobs failed, citing missing permissions on the Snapshot Resource Group.
- Impact: 100% failure rate for long-term retention copies.

#### Diagnostic Verification

An exhaustive RBAC audit was performed to confirm the presence of all three required identities against the Snapshot Resource Group:

1. Vault MSI held `Reader` on the AKS Cluster.
2. Vault MSI held `Reader` on the Snapshot RG.
3. Cluster User-Assigned Identity (`uai-ff-uks-gp-aks`) held `Contributor` on the Snapshot RG.

#### Escalation Path

The Azure CLI explicitly confirmed these permissions were "already assigned", yet backup operations immediately failed with the same permissions error. This indicates a platform-level desynchronisation between Microsoft Entra ID and the Azure Backup service.

Next Action: Open a support ticket with Microsoft, providing the validated Entra ID role assignments alongside the reproducible failure logs.

#### Security Posture Adjustments

- Discovered `AllowBlobPublicAccess` was set to `True` at the account level (worse posture than MKUH).
- Verified no individual containers were actively exposing data (`PublicAccess: null`).
- This requires an infrastructure hardening task to toggle the account-level setting to `False`.

### ZRS Migration Procedure (FTFL-525)

To meet the 10km redundancy requirement, backup storage accounts were converted from `Standard_LRS` to `Standard_ZRS`.

Crucial Technical Detail: Attempting to flip the SKU property via a standard `az storage account update` command results in an `InvalidValuesForRequestParameters` error. Moving to zone redundancy requires the customer-initiated migration command.

#### Execution Command

```sh
az storage account migration start \
  --account-name <Storage-Account-Name> \
  --resource-group <Backup-RG-Name> \
  --sku Standard_ZRS \
  --name default \
  --no-wait
```

#### Verification Command

Migration is an asynchronous background task that can take up to 72 hours. Status can be polled using:

```sh
az storage account migration show \
  --account-name <Storage-Account-Name> \
  --resource-group <Backup-RG-Name>
```

### Key Troubleshooting Takeaways

- Trust but Verify: An overall `ProtectionConfigured` state on a backup instance does not guarantee successful tiering. Job history must be queried independently.
- RBAC Propagation: Role assignment changes require up to 30 minutes to propagate across the management plane before subsequent tiering jobs will succeed.
- Ad-Hoc Limitations: Azure Backup for AKS blocks ad-hoc triggers for specific retention tiers (e.g., forcing a "Daily" tag). Triggering must be done using an overriding rule against the base operational schedule.--
