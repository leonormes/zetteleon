## SoT - Semantic Code Graph

### The Core Insight

To optimize LLM reasoning, code must be projected as a Semantic Maze (Data Lineage + Domain Invariants) rather than a raw Syntax Tree (Files + Text). This filters syntactic "noise" to expose the "Human Description" that anchors the model's latent space.

### The Problem: The Collector's Fallacy in Code

Feeding an LLM raw source files (ASTs) is inefficient because:

1. High Entropy: Syntax, imports, and boilerplate consume token windows without adding semantic value.
2. Myopic Focus: The model sees the _local_ file structure but misses the _global_ system architecture.
3. Context Rot: Irrelevant details distract the model, leading to "parochial" code generation (correct syntax, wrong domain).

### The Solution: The Information Structure

Instead of "Data Structures" (machine-readable), we present "Information Structures" (intelligence-readable).

#### Layer 1: The Skeleton (The Symbol Table)

- What: Function signatures, class definitions, and docstrings.
- Why: Defines _what is possible_ without showing _how it is implemented_.
- Mechanism: `calculate_tax(amount: Money) -> Money` tells the LLM enough to use the function without seeing the math.

#### Layer 2: The Maze (Data Lineage)

- What: A trace of data flow across the system (e.g., "UserEmail enters at API -> Normalised in Service -> Stored in DB").
- Why: Reveals "Complex" side effects (State Mutation, IO, API calls) that static analysis misses.
- Metaphor: The "Subway Map" vs The "Satellite Photo".

#### Layer 3: The Manifesto (Domain Constraints)

- What: A set of immutable "Laws of Physics" for the domain (e.g., "Invoices cannot exist without a Customer").
- Why: Prunes the probability tree. If the LLM knows "No ORM allowed", it will never hallucinate ORM code.

### The Mechanism: Perplexity Reduction

LLMs are probability engines. Providing "Information" is not about teaching wisdom; it is about constraining the search space.

- Low Constraints: "Write a user function" -> 1,000 possible paths (High Perplexity).
- High Constraints: "Write a user function using only Raw SQL and the `User` Entity" -> 1 path (Low Perplexity).

### Ubiquitous Language (The Glossary)

To anchor the LLM's vector space, we must enforce a strict domain vocabulary.

- Example: Use "Bead" instead of "Log" to force the model into the specific architectural context of the system.
- See [[Protocol - Context Injection]] for the implementation.

## ## Ubiquitous Language (The Glossary)

### FS-DB: The Implementation Layer (Surgeon V2)

We are moving from "Context Injection" (Soft/Prompt-based) to "Structural Determinism" (Hard/Tool-based). The filesystem itself becomes the database (`FS-DB`).

#### 1. The `structure.graph` (The RIG)

A deterministic, build-centric map of the repository.

- Nodes: Buildable units (libs, bins), Aggregators (workspaces), Runners (tests).
- Edges: Hard dependencies (imports, links) and Coverage links.
- Goal: Provide the LLM a "Map of the Territory" before it reads the "Terrain."

#### 2. The `_meta.json` (Atomic Grounding)

Local metadata files generated by Tree-sitter to preserve scope.

- Schema:

  ```json
  {
    "symbol": "AuthService",
    "type": "class",
    "scope": "internal",
    "invariants": ["No raw pointers", "Atomic updates only"],
    "dependencies": ["DatabaseDriver", "ConfigLoader"]
  }
  ```

#### 3. Verification: Pass@Architect

Measuring "Architectural Drift" using an LLM-as-a-Judge.

- Metric: Percentage of generated snippets that satisfy the `Meta-Context` axioms.
- Action: If Drift > 5%, the build fails.
