> Canonical status: this note is the authoritative spec for what may live in `20_Thinking/21_Workbench/`. It is the workbench counterpart to [[SoT - ProdOS Frontmatter Contract (Note Type Schemas)]] (note-level schema) and [[SoT - Typed Edge Vocabulary (Knowledge Graph Relations)]] (edges). Where this note and a prompt disagree, this note wins. `AGENTS.md` §0 and [[Reference - File Structure]] §D link here.

## Minimum Viable Understanding (MVU)

A HEAD note is an open question the human owns—one unresolved thing that requires _his_ judgement, parked somewhere he will see it. It is not a capture, not a summary, not a document, and not a finished piece of analysis. The workbench is a queue of live thinking, and its usefulness is a direct function of how short it is: a workbench holding 44 items where 22 are web clippings is not a queue, it is a second inbox that nobody triages.

This contract exists because the workbench silently became that. The Obsidian Web Clipper was writing captures straight into `20_Thinking/`, which meant the folder's signal—_these are the things I am currently thinking about_—was diluted to the point of uselessness. Capture now goes to `00_Inbox/`. The workbench holds questions.

The corollary matters as much as the rule: an unresolved tension recorded inside a canonical SoT is invisible. It sits in a note the reader consults for answers, in a section they skim. Tensions belong in the queue they will actually be worked from, with the SoT retaining a one-line pointer so its reader still knows the note is not settled.

## 1. The Four Compliance Tests

A note in `20_Thinking/21_Workbench/` MUST pass all four. Each is binary—if you have to argue for a pass, it is a fail.

| # | Test | Question | Fail → |
|:--|:-----|:---------|:-------|
| 1 | Ownership | Does this contain at least one unresolved question that is _mine_ to resolve—requiring my judgement, values, or context, not just a lookup? | `00_Inbox/` |
| 2 | Origin | Was this generated by thinking—mine, or a dialogue I took part in—rather than captured from an external source? | `00_Inbox/` |
| 3 | Convergence | Is the question still open? A note whose question has been answered is finished thinking, not active thinking. | Chronos → SoT, then `50_Archive/` |
| 4 | Actionability | Does it state what would settle it—the evidence, experiment, decision, or conversation that closes the thread? | Fix in place (add the section) |

### 1.1 The Origin Test is Mechanical

Any of these frontmatter keys is an automatic Origin failure, no judgement required:

```
source:  source_url:  url:  author:  published:  captured:  clipped:
```

These are the Web Clipper's signature. A note carrying them is a capture. It may be _interesting_, it may later _provoke_ a HEAD note—but it is not itself thinking, and it goes to `00_Inbox/` for normal ingest via [[Prompt - Vault Ingest Router]].

A capture that genuinely provoked a question does not get to stay by association. Route the capture to the inbox, and write a _separate_ HEAD note stating the question it provoked, linking back to it. The question is the thinking; the article is the stimulus.

### 1.2 What the Workbench is not

| Not a HEAD note | Where it goes |
|:---|:---|
| Web article, video summary, clipped page | `00_Inbox/` |
| Finished engineering analysis / RCA / design writeup | `30_Library/200_Projects/` |
| Checklist, runbook, per-site procedure | `30_Library/SoT/` as a `Protocol -` note |
| Vault audit output, migration report | `90_Audits/` |
| Meeting notes, raw transcript | `00_Inbox/` |
| Settled knowledge | `30_Library/SoT/` via [[Prompt - ProdOS Chronos Synthesizer]] |
| A task | Todoist. The vault does not hold actions. |

## 2. Schema

A HEAD note is a `QuestionNote` that happens to live in the workbench. It inherits the `QuestionNote` schema from [[SoT - ProdOS Frontmatter Contract (Note Type Schemas)]] §3.4 rather than inventing a parallel one.

```yaml
---
title: "HEAD - <the question, ending in ?>"
type: question
tension: "<the belief or observation that generates this question>"
candidate_answers: []          # may be empty; that is honest
related_claims: []             # wikilinks to claims/SoTs this bears on
sources: []                    # wikilinks to notes this tension was harvested from
tags: [state/thinking, prodos/head]
conformant: true
prodos:
  kind: head
  lifecycle: active            # active | stable (=resolved, ready for Chronos)
status: open                   # open | thinking | resolved
AoL: Personal                  # Personal | Work | System — area of life, drives Thinking.base views
closing_condition: true        # false = Test 4 not yet satisfied; surfaces in the "No exit condition" view
created: <ISO8601>
modified: <ISO8601>
---
```

### 2.3 Why `AoL` and `closing_condition` Exist

Both are here to make `02_bases/Thinking.base` work, and both encode a compliance test rather than a taxonomy:

- `AoL` splits the queue three ways—`Personal`, `Work`, `System` (vault and tooling). Without it the workbench is one undifferentiated list, and a personal question about solitude sits next to a question about compiler flags, which makes neither approachable. The value is what you can act on _in the mood you are currently in_.
- `closing_condition` is Test 4 made queryable. Bases can only read frontmatter, so "does this note have a `## What Would Settle It` section that says something" has to be mirrored into a boolean. `false` means the thread has no exit, which is the precise condition under which a HEAD note rots. The base's No exit condition view is the enforcement surface.

Set `closing_condition: false` honestly. A note that claims an exit condition it does not have is worse than one that admits it has none, because it never appears in the view that would prompt you to give it one.

### 2.1 Title Format

`HEAD - <question>?`—the title MUST be a question ending in `?`.

This is a forcing function, not decoration. "HEAD - The Trap of the Architect" tells you a topic; "HEAD - Am I using architecture work to avoid physical initiation?" tells you what is actually unresolved, and lets you notice when it stops being unresolved. A topic can sit open forever without anybody feeling the debt. A question cannot.

Legacy notes are not auto-renamed. Renaming rewrites every backlink and is a human decision; non-question titles on pre-2026-08-03 notes are flagged by the sweep, never changed by an agent.

### 2.2 Body Structure

```markdown
## The Question
<one paragraph — the open thing, stated plainly>

## Why It Matters
<what decision, belief, or piece of work is downstream of this>

## What I Currently Think
<the current lean, including "no idea" if that is true>

## What Would Settle It
<the evidence, experiment, decision, or conversation that closes the thread>

## Sources
<wikilinks to the SoT/claim notes this was harvested from>
```

`## What Would Settle It` is the section that makes the difference between a thread and a rumination. A HEAD note that cannot name its own closing condition is one that will still be open in a year.

## 3. Lifecycle

```
capture ──→ 00_Inbox ──→ [Vault Ingest Router] ──→ 30_Library
                                │
                                ↓ (provokes a question)
   tension in an SoT ──→ 20_Thinking (HEAD) ──→ [Chronos] ──→ SoT + Next Test
                                │                                  │
                                └──── still open ←─────────────────┘
```

A HEAD note leaves the workbench in exactly two ways:

1. Resolved—[[Prompt - ProdOS Chronos Synthesizer]] folds the answer into an SoT and the HEAD note is archived. The SoT's `Open threads:` pointer (§4) drops the link.
2. Abandoned—the question stopped mattering. Say so explicitly in the note, set `status: resolved`, archive. An abandoned question is a legitimate outcome; a silently rotting one is not.

There is no third exit. A note that has been `status: open` for six months is a signal about the question, and the sweep (§5) surfaces it.

## 4. Tensions Live in the Queue, Pointers Live in the Canon

A canonical note (`SoT`, `Claim`, `MoC`, project) MUST NOT carry a `## Tensions & Gaps`, `## Open Questions`, or equivalent prose section. Those sections are where open problems go to be forgotten—the reader of an SoT is looking for the answer and skims past the caveats.

Instead, the canonical note carries a single pointer line directly beneath its `MVU`/opening section:

```markdown
> Open threads: [[HEAD - Does Tesler's Law generalise beyond software?]] · [[HEAD - What is the observable tell for bad faith, before I disengage?]]

```

This preserves the one thing the inline section was genuinely good at—warning a reader at the point of reading that the note is not settled—while moving the thinking itself somewhere it will be worked.

Scope limit. This applies to _unresolved_ tensions. A note may still record a _documented trade-off_ or _scope boundary_ in prose (e.g. "the compiler deliberately does not parse visible inline fields")—that is settled knowledge about a limitation, not an open question. The test: can it be closed? If yes, it is a tension and belongs in a HEAD note. If it is a permanent property of the design, it stays in the SoT as prose.

## 5. Enforcement

- [[Protocol - Workbench Compliance Sweep]]—runs the four tests over every note in `20_Thinking/21_Workbench/`, routes failures, and reports stale threads. Recurring.
- [[Prompt - Tension Harvester]]—harvests `## Tensions` sections from canonical notes into clustered HEAD notes and rewrites the source into a §4 pointer. One-off per domain, then on demand.

Agent write scope into `20_Thinking/` is now defined rather than forbidden: an agent MAY create a HEAD note and MAY move a non-compliant note out, but MUST NOT edit the body prose of a human-authored HEAD note. See `AGENTS.md` §0 and §6.

## 6. Why Questions and not Topics

The workbench is working memory, and working memory is expensive. Everything in it costs attention every time you look at the folder. A topic-shaped note ("The Trap of the Architect") has no closing condition, so it never leaves—it accumulates, and the folder degrades into a graveyard that is psychologically easier to ignore than to read. That is the failure mode this contract is built against, and it is the same failure mode the Web Clipper produced by a different route: anything that can enter the workbench without a defined exit will fill it.

A question has an exit by construction. That is the whole design.
