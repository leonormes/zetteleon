## AI-Generated Code Without Human Review Creates Production Risk

An LLM can generate code that looks syntactically correct, runs without crashing locally, and still contain:

- Architectural flaws (wrong patterns, missing async handling, improper error propagation)
- Security vulnerabilities (prompt injection, SQL injection, insufficient input validation)
- Silent failures (logic that runs but produces wrong results)
- Unmaintainable patterns (incomprehensible structure, missing documentation, violations of project conventions)

None of these problems are caught by the fact that the code "works" in a quick test. They emerge in production under load, edge cases, or months later during maintenance.

### Scope & Conditions

Applies to AI-generated code destined for production systems where downtime, data loss, or security breaches have real consequences.

### Evidence

Source: "Nobody Pages the LLM: Engineering Rigour for Vibe Coding" (Ritesh Modi). Direct quotes:

> "Without human oversight, the code may be bug-ridden, architecturally flawed, and unlikely to survive in a production environment" [04:59]

> "AI generates the code, but you own the delivery. If an AI-generated app breaks at 3:00 AM, the developer is responsible for the downtime and technical debt, not the LLM" [07:07]

### Implications

- Deferred accountability: The LLM has no stake in the outcome. The developer (and the business) absorbs all risk.
- Debt avalanche: Unreviewed code shipped to production accumulates technical debt that compounds. Fixing it becomes exponentially more expensive than catching it in review.
- Security blind spots: LLMs are trained on public code, including insecure code. They have no mechanism to reliably avoid known vulnerability patterns.

### Counterargument

Not all AI-generated code is wrong. Some tasks (scaffolding, boilerplate, well-understood domains) have high success rates. The question is: which tasks are safe, and who decides?
