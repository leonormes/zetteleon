## The Representational Fallacy

The representational fallacy is the view that structure is secondary to facts: first there are facts, then they are structured to make them manageable. On that view a type documents what a function does and a schema represents reality. The SoT calls the view a structural category error for formal systems.

### Scope & Conditions

- The SoT applies the label inside formal systems. Outside them the representational view is often right, and [[The Map is Not the Territory]] is the sound form of it: a map is a model of a territory that exists independently.
- It is distinct from that principle because it concerns systems where the rules, not an outside territory, decide what counts as a valid fact.
- "Fallacy" is the SoT's strong word. Whether it is a mistake in every formal domain is the question raised by [[Shared Formal Attributes Across Domains May Be a Family Resemblance and Not an Ontological Equivalence]].

### Evidence

> "The naive view holds that structure is secondary. First, there are facts; then we structure them to make them manageable. The type documents what the function does. The CDM schema represents clinical reality. The state file describes the running infrastructure. The task list records what exists in the mind."
> ([[SoT - Structure is Truth is a Unifying Axiom Across Formal Systems]], §1 The Representational Fallacy, emphasis markers omitted)

> "This view is a structural category error."
> (same section)

### Implications

- Naming the view lets a design review ask which view a team is working from. A team that treats a schema as documentation will let it lag behind the code, and a team that treats it as constitutive will fix the code.
- The three tests for telling the views apart are in [[How to Test Whether a Structure Is Constitutive or Merely Representational]].
