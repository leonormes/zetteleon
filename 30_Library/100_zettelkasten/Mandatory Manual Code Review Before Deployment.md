## Mandatory Manual Code Review Before Deployment

In traditional software engineering, code review is a quality gate. In AI-assisted development, it becomes a load-bearing requirement: a human must read and understand the generated code before it ships.

This is not optional, not subject to time pressure, and not something that LLM-to-LLM review can replace entirely.

### Scope & Conditions

Applies to any AI-generated code destined for production. Codebases where "maintainability" and "understanding" are not requirements (e.g., throwaway scripts, one-off data processing) might skip this, but anything owned long-term requires it.

### Evidence

Source: "Nobody Pages the LLM: Engineering Rigour for Vibe Coding" (Ritesh Modi). Direct quote: "You must have at least two human reviews before pushing any code. If you do not understand the code the AI wrote, you cannot reliably maintain it" [17:47].

### Implications

- Slowdown, not speedup: If generating code takes 5 minutes but reviewing it takes 2 hours, the LLM hasn't saved time; it's replaced manual writing with manual review. The win is in cognitive load (different kind of work), not pure velocity.
- Domain knowledge as moat: Developers who can quickly evaluate AI-generated code (spot the mistakes, understand the architecture) become more valuable than developers who can write code from scratch, because they can review and redirect the LLM's output.
- Consistency checks needed: The first review catches bugs. The second review catches inconsistencies with project conventions, style, and architectural decisions that the first reviewer might miss.

### LLM-to-LLM Review Is Insufficient

LLMs can review other LLM-generated code (checking for consistency, potential bugs, style violations). But:

- LLMs hallucinate "fixes" to non-existent problems.
- LLMs cannot catch architectural mismatches outside their training data.
- LLM reviewers lack accountability—a human reviewer who signs off on buggy code owns part of the failure.
