Find research into the different ways we can query omop. We are trying to create an interface that allows researchers to describe what cohorts they want without having to write complex SQL. We are limited in our SQL that carries out their queries on their behalf to only read operations.

This analysis outlines the architectural patterns for querying the OMOP Common Data Model (CDM) without direct SQL authoring.

Given your limitation to **read-only operations** (SELECT privileges only), standard OHDSI tools present a specific architectural challenge: the standard "Cohort Generation" process typically requires **write** access to a scratchpad schema (to instantiate `cohort` tables). Your solution must therefore decouple **Definition** (client-side/app-side) from **Execution** (database-side), or rely entirely on transient execution (CTEs/Temp tables).

### 1. The Standard Model: JSON Serialization (Circe)

This is the prevailing mental model in the OHDSI community. You do not generate SQL directly; you generate a JSON object that represents the logic, which a compiler translates into SQL.

- **Mechanism:** The user interacts with a UI. The UI constructs a standard JSON artifact (a "Cohort Definition"). A library (Circe) compiles this JSON into OHDSI-compliant SQL.
- **The Component:****Atlas** (the GUI) and **WebAPI** (the backend service).
- **Relevance to You:** You can bypass the Atlas UI and implement your own frontend that generates **Circe-compliant JSON**. You then pass this JSON to the WebAPI (or use the R libraries `CirceR` / `SqlRender`) to generate the SQL string.
- **Read-Only Implication:** The SQL generated by Circe is often designed to `INSERT` people into a `COHORT` table. You would need to parse the generated SQL to strip the `INSERT` / `CREATE` statements, keeping only the selection logic (CTEs and SELECTs) to display results dynamically.

### 2. The DSL Model: Programmatic Abstraction (Capr)

If your researchers are comfortable with code but not SQL (e.g., epidemiologists using R), or if you are building a backend service that assembles queries programmatically, this is the most efficient structural approach.

- **Mechanism:** Use a Domain Specific Language (DSL) that wraps OMOP logic into objects (e.g., `Condition(X)` occurring before `Drug(Y)`).
- **Key Tool:****Capr** (an R package). It treats cohort definitions as composable objects.
- **Why it works:** It enforces the "Concept Set" model. Users define *concepts* (codes) and *logic* (temporal relationships) separately. Capr compiles this directly to the OHDSI SQL dialect.
- **Read-Only Implication:** Like Circe, Capr output defaults to creating tables. You will need to intercept the SQL generation step to ensure it executes as a transient query or simply returns the code to the user.

### 3. The Natural Language Model (LLM/NLP)

This approach replaces the "Visual Builder" with a text prompt. This is currently the active frontier of OMOP research.

- **Mechanism:** An LLM or NLP pipeline translates free text ("Male patients over 50 with T2D taking Metformin") into structured logic or SQL.
- **Key Tools & Research:**
	- **Criteria2Query (C2Q):** An OHDSI tool that parses clinical text (like trial eligibility criteria) and converts it into the JSON standard mentioned in Model 1. It acts as a bridge between NL and the structured OHDSI ecosystem.
	- **OMOP Navigator:** Recent research into using LLMs (like GPT-4) to write OMOP SQL directly.
	- **Text-to-SQL (RAG):** Providing an LLM with the OMOP schema and a "Concept Lookup" tool allows it to write high-quality SQL.
- **Warning:** LLMs struggle with the specific concept IDs (e.g., knowing that "Type 2 Diabetes" is concept ID `201826`). A "Retrieval Augmented Generation" (RAG) architecture is mandatory here: the interface must first look up the Concept IDs, then ask the LLM to build the query using those specific IDs.

### 4. The Simplified "Visual Query Builder"

If Atlas is too complex, you can build a simplified abstraction layer that limits the user's freedom but guarantees valid SQL.

- **Mechanism:** A "Block" interface (e.g., Scratch or Blockly for cohorts).
- **Structure:**
	1. **Concept Selection:** User searches and selects standard concepts.
	2. **Temporal Logic:** User selects pre-defined relationships ("Before", "During", "On Same Day").
	3. **Filter Logic:** Age, Gender, Date Range.
- **SQL Generation:** You map these UI blocks to parameterised SQL templates (`SqlRender` can be used for parameter substitution). This is safer than raw SQL generation.

### Architectural Recommendation: The Read-Only Problem

Since you are limited to **read-only** SQL, you cannot use the standard "Cohort Generation" pattern (which writes persistent results). You have two paths:

1. **Transient CTEs (Common Table Expressions):** Your SQL generator must nest the logic into a massive `WITH` clause, ending in a `SELECT count(*) FROM final_cohort`. This is computationally expensive and provides no persistence (you can't save the cohort for later), but it satisfies the read-only rule.
2. **The "Definition Store" Pattern:** You store the *definition* (the JSON or logic) in your application database (not the OMOP database). When a researcher wants to "run" it, you generate the SQL on the fly, execute it as a read-only query to get a preview/count, but never attempt to write the cohort back to the OMOP CDM.

The Circe JSON schema is structured as a **serialised object model** that strictly decouples **vocabulary** (What is "Diabetes"?) from **logic** (When did it happen?).

As a software architect, you should view this not as a "query script" but as a **configuration state** for a cohort builder.

### 1. High-Level Architecture

The root object has four primary components. For a read-only interface, you primarily care about the first three.

| Component | Type | Purpose | Architect's Note |
| --- | --- | --- | --- |
| **`ConceptSets`** | `Array` | The "Dictionary." Defines groups of medical codes. | Decoupled. Logic references these by Integer ID. |
| **`PrimaryCriteria`** | `Object` | The "Index Date." Defines the entry event(s). | Equivalent to the `FROM` clause + Initial `WHERE`. |
| **`InclusionRules`** | `Array` | The "Filters." Boolean logic applied relative to the index. | Equivalent to subsequent `WHERE` or `HAVING` clauses. |
| **`CensoringCriteria`** | `Array` | The "Exit." When a person leaves the cohort. | Less relevant for simple "count" queries. |

### 3. Key Architectural Concepts

#### A. The Vocabulary Indirection (ConceptSets)

- **Mechanism:** You never hardcode concept IDs into the logic. You create a `ConceptSet` (ID: 0), populate it with IDs (e.g., `201826`), and set flags (`includeDescendants: true`).
- **Usage:** The logic simply requests `CodesetId: 0`.
- **Benefit:** This allows you to update the definition of "Diabetes" in one place without breaking the temporal logic.

#### B. The Event Object (Criteria)

- Every domain (Drug, Condition, Procedure) has its own object key (e.g., `ConditionOccurrence`, `DrugExposure`).
- These objects act as **wrappers** for the SQL parameters.
- **Attributes:**
	- `CodesetId`: Which concepts to look for.
	- `Age`: Integer range filter.
	- `Gender`: Array of concept IDs.
	- `OccurrenceStartDate`: Date range filter.

#### C. The Relational Logic (StartWindow)

- In `InclusionRules`, criteria are not absolute dates; they are **relative** to the `PrimaryCriteria` index date.
- **Schema:**
	- `Start`: `{ "Days": 0, "Coeff": -1 }` (0 days * -1 = 0 days Before index).
	- `End`: `{ "Days": 30, "Coeff": 1 }` (30 days * 1 = 30 days After index).

### 4. Implementation Strategy for Read-Only

The standard OHDSI stack uses this JSON to generate a `CREATE TABLE` statement. Since you are read-only, you must intervene in the pipeline.

**Option A: The Wrapper (Easiest)**

1. Generate the standard JSON in your UI.
2. Send it to the standard OHDSI library (`SqlRender` / WebAPI) to generate the SQL.
3. **Intercept the SQL string.**
4. Regex/String replace the `CREATE TABLE #cohort...` and `INSERT INTO...` headers.
5. Wrap the logic in a Common Table Expression (CTE) or a subquery.
	- *From:*`INSERT INTO results (subject_id) SELECT...`
	- *To:*`WITH cohort AS (SELECT...) SELECT COUNT(*) FROM cohort;`

**Option B: The Custom Compiler (Cleanest)** Since you likely only need a subset of OHDSI features (e.g., "Count patients with X and Y"), you can write a lightweight transpiler.

1. UI outputs a simplified JSON.
2. Backend maps `ConceptSet` to `SELECT concept_id FROM concept_ancestor...`.
3. Backend maps `PrimaryCriteria` to `SELECT person_id FROM condition_occurrence...`.
4. Backend joins them using `INTERSECT` or `INNER JOIN`.

### The Core Type System

This is the "Concept Dense" view. The architecture relies on three distinct layers:

1. **Vocabulary Layer:** Defines *what* (Concepts).
2. **Temporal Layer:** Defines *when* (Windows).
3. **Logical Layer:** Defines *logic* (Groups/Intersections).

TypeScript

```ts
// ---------------------------------------------------------
// 1. Root Aggregate
// ---------------------------------------------------------
export interface CohortExpression {
  Title?: string; // Metadata only
  ConceptSets: ConceptSet[];
  PrimaryCriteria: PrimaryCriteria;
  InclusionRules: InclusionRule[];
  CensoringCriteria: Criteria[]; // Often empty for simple read-only counts
  CollapseSettings: CollapseSettings;
  ExpressionLimit: ResultLimit;
}

// ---------------------------------------------------------
// 2. Vocabulary Layer (The "Dictionary")
// ---------------------------------------------------------
export interface ConceptSet {
  id: number; // Referenced by 'CodesetId' in criteria
  name: string;
  expression: {
    items: ConceptSetItem[];
  };
}

export interface ConceptSetItem {
  concept: Concept;
  includeDescendants: boolean;
  isExcluded: boolean;
  includeMapped: boolean;
}

export interface Concept {
  CONCEPT_ID: number;
  CONCEPT_NAME: string;
  STANDARD_CONCEPT?: string; // 'S', 'C', or null
  INVALID_REASON?: string; // 'V' or null
  DOMAIN_ID: string; // 'Condition', 'Drug', 'Measurement', etc.
  VOCABULARY_ID: string;
  CONCEPT_CODE: string;
}

// ---------------------------------------------------------
// 3. Temporal & Logical Layer (The "Engine")
// ---------------------------------------------------------

// The "Entry Event" configuration
export interface PrimaryCriteria {
  CriteriaList: Criteria[]; 
  ObservationWindow: ObservationWindow;
  PrimaryCriteriaLimit: ResultLimit;
}

// The "Filter" configuration (Boolean Logic)
export interface InclusionRule {
  name: string;
  description?: string;
  expression: CriteriaGroup;
}

// Recursive Grouping for (A OR B) AND C logic
export interface CriteriaGroup {
  Type: 'ALL' | 'ANY' | 'AT_LEAST' | 'AT_MOST'; 
  Count?: number; // Used if Type is AT_LEAST/AT_MOST
  CriteriaList: CorerelatedCriteria[]; // Leaf nodes
  Groups: CriteriaGroup[]; // Recursive branch nodes
  DemographicCriteriaList?: DemographicCriteria[];
}

// Links a domain criteria to a time window relative to the Index Date
export interface CorerelatedCriteria {
  Criteria: Criteria; // The "What"
  StartWindow: Window; // The "When" (Start date logic)
  EndWindow?: Window;  // The "When" (End date logic, rarely used)
  RestrictVisit: boolean; // Restrict to same visit as index?
}

// ---------------------------------------------------------
// 4. Domain Criteria (The "Data Wrappers")
// ---------------------------------------------------------

// Union type of all supported clinical events
export interface Criteria {
  ConditionOccurrence?: ConditionOccurrence;
  DrugExposure?: DrugExposure;
  ProcedureOccurrence?: ProcedureOccurrence;
  Measurement?: Measurement;
  VisitOccurrence?: VisitOccurrence;
  // ... expand for Device, Observation, etc.
}

// Base interface for clinical events
interface CriteriaBase {
  CodesetId?: number; // Links to ConceptSet.id
  First?: boolean;    // Only the first occurrence?
  Age?: IntegerRange;
  Gender?: Concept[]; // Hardcoded Gender concepts (e.g. 8507 for Male)
  OccurrenceStartDate?: DateRange;
}

export interface ConditionOccurrence extends CriteriaBase {
  ConditionType?: Concept[]; // e.g. 'EHR diagnosis' vs 'Claims'
  StopReason?: TextFilter;
  ConditionSourceConcept?: number; // Source vocabulary ID
}

export interface DrugExposure extends CriteriaBase {
  DrugType?: Concept[];
  Refills?: IntegerRange;
  Quantity?: IntegerRange;
  DaysSupply?: IntegerRange;
}

export interface ProcedureOccurrence extends CriteriaBase {
  ProcedureType?: Concept[];
  Modifier?: Concept[];
}

export interface Measurement extends CriteriaBase {
  Operator?: Concept[]; // <, >, =
  ValueAsNumber?: NumberRange;
  Unit?: Concept[];
}

export interface VisitOccurrence extends CriteriaBase {
  VisitType?: Concept[];
  VisitSourceConcept?: number;
  VisitLength?: IntegerRange;
}

// ---------------------------------------------------------
// 5. Utility Types (Ranges & Windows)
// ---------------------------------------------------------

export interface Window {
  Start: WindowEndpoint;
  End: WindowEndpoint;
  UseEventEnd?: boolean; // If true, relative to event end date, not start
}

export interface WindowEndpoint {
  Days: number | null; // null implies "All time"
  Coeff: -1 | 1;      // -1 for "Before", 1 for "After"
}

export interface ObservationWindow {
  PriorDays: number;
  PostDays: number;
}

export interface ResultLimit {
  Type: 'First' | 'Last' | 'All';
}

export interface CollapseSettings {
  CollapseType: 'ERA' | 'SO'; // Era vs Selected Occurrence
  EraPad: number;
}

export interface IntegerRange {
  Value?: number;
  Op: 'lt' | 'lte' | 'eq' | 'gt' | 'gte' | 'bt'; // Less than, equal, between...
  Extent?: number; // Used for 'bt' (between) as the upper bound
}

export interface NumberRange extends IntegerRange {
  // Same structure, just semantically allows floats
}

export interface DateRange {
  Value?: string; // YYYY-MM-DD
  Op: 'lt' | 'lte' | 'eq' | 'gt' | 'gte' | 'bt';
  Extent?: string;
}

export interface TextFilter {
  Text: string;
  Op: 'startsWith' | 'endsWith' | 'contains' | '!startsWith' | '!endsWith' | '!contains';
}

interface DemographicCriteria {
    Age?: IntegerRange;
    Gender?: Concept[];
    Race?: Concept[];
    Ethnicity?: Concept[];
    OccurrenceStartDate?: DateRange;
    OccurrenceEndDate?: DateRange;
}
```

### Architectural Considerations for Read-Only Implementation

1. **The `CodesetId` Pointer:**Ensure your UI enforces referential integrity. A `ConditionOccurrence` object cannot contain a `CodesetId: 1` if `ConceptSets` does not contain an entry with `id: 1`.
2. **The Window Coefficient:**The `Coeff` field is critical.
	- `Days: 30, Coeff: -1` = 30 Days **Before** Index.
	- `Days: 30, Coeff: 1` = 30 Days **After** Index.
	- Failing to set this correctly is the most common logic error in custom OHDSI implementations.
3. **Recursive Groups:**The `CriteriaGroup` interface is recursive (`Groups: CriteriaGroup[]`). This allows nesting:
	- *Top Group:*`Type: ALL` (Must match everything below)
		- *Child 1:*`Type: ANY` (Match A OR B)
		- *Child 2:*`DrugExposure` (Match C)
	- Your UI must handle this recursion if you want to support complex Boolean logic.
