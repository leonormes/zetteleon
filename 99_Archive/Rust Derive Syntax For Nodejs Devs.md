Which path shall we start with?

The "Auto-Polyfill" Model (Logic)

In the **"Auto-Polyfill"** model, think of `#[derive]` as a compile-time script that reads your `enum` definition and writes the implementation logic for you. In Node.js, you might manually write a `clone()` method or use a library like `lodash.isEqual`. In Rust, the compiler generates this code so you don't have to.

When you use `#[derive(Debug, Clone, PartialEq, Eq)]`, the compiler effectively "polyfills" your `enum` with the following logic:

### 🛠️ How the Polyfill Works

- **`Debug`** 🔍: It writes a `fmt` method. It looks at the name `IncrementStrategy` and the names of the variants (`Major`, `Minor`, etc.). If you print it, it knows to output the string `"Major"` or `"Custom(...)"`.
- **`Clone`** 👥: It generates a `clone()` method. For simple variants like `Major`, it just returns a copy. For `Custom(SemanticVersion)`, it calls `.clone()` on the internal `SemanticVersion` data.
- **`PartialEq`** ⚖️: It writes the `==` logic. It generates a large `match` statement (similar to a `switch` in TypeScript) that checks: "Are these the same variant? If so, is the data inside them also equal?"

---

### 🧠 The "Concept Density" of Custom(SemanticVersion)

This is where the model gets interesting for a TypeScript dev. Because Rust enums are **Sum Types** (they can hold data), the `derive` macro has to be recursive.

When the compiler generates the `PartialEq` polyfill for your `enum`, it looks like this conceptually:

TypeScript

```markdown
// Conceptual TypeScript "Polyfill" generated by Derive
function equals(a: IncrementStrategy, b: IncrementStrategy): boolean {
    if (a.type !== b.type) return false; // Different variants are never equal
    
    if (a.type === 'Custom' && b.type === 'Custom') {
        // It RECURSIVELY calls the equality check on the inner data
        return a.value.equals(b.value); 
    }
    
    return true; // Simple variants (Major, Minor) with same type match
}
```

Because of this, `derive` only works if **every piece of data inside the enum** also implements that trait. If `SemanticVersion` didn't have `PartialEq`, your `IncrementStrategy` couldn't "derive" it either.

### 🧩 Structural vs. Nominal Requirements

In TypeScript, you might use an interface to ensure a property exists. In Rust, `derive` ensures the **logic** exists.

- **TypeScript**: If you have `interface A { x: number }`, any object with a numeric `x` fits.
- **Rust**: If you want to `derive(PartialEq)`, the compiler must find an existing `impl PartialEq` for every field. It doesn't care about the *shape* of the data as much as the *capabilities* of the data.

Trait Bounds 📐: The "Architectural Contract" that defines what a type must be able to do to be used in certain generic functions or structures.

In Rust, **Trait Bounds** act as the "Type Constraints" you might find in TypeScript generics (e.g., `<T extends SomeInterface>`). They define the requirements for a generic type.

Think of it as a **Structural Contract**: "I don't care what your underlying data is, as long as you provide these specific methods."

When you use `derive`, you are effectively fulfilling these contracts. If you want to write a function that works for any versioning strategy, you use a bound to ensure that strategy can be printed or copied safely.

### 🧩 The Generic Architecture

In TypeScript, you might write:

TypeScript

```markdown
function logAndCopy<T extends { clone(): T }>(item: T): T {
    console.log(item);
    return item.clone();
}
```

In Rust, the same architectural pattern looks like this:

Rust

```markdown
// The 'T: Clone + Debug' part is the Trait Bound
fn process_strategy<T: Clone + std::fmt::Debug>(strategy: T) -> T {
    println!("Processing: {:?}", strategy); // Requires Debug
    strategy.clone()                        // Requires Clone
}
```

### 🌉 The "Dependency Injection" of Logic

Trait bounds allow you to decouple your logic from specific data types. This is highly "concept dense" because:

- **Static Dispatch**: The compiler creates a specific version of your function for every type you use (similar to C++ templates), meaning there's zero runtime overhead for the abstraction.
- **Combinatorial Power**: You can stack bounds using `+`. If a type must be both `Clone` and `PartialEq`, you simply state `T: Clone + PartialEq`.

###1. The Single Colon (:)—The "Is-A" Operatoror

In the context of generics, the single colon defines a **Constraint** (Trait Bound). It tells the compiler: "This generic variable `T` is not just *anything*; it must be a type that implements these specific interfaces."

- **TypeScript Mental Model**: `T extends Clone`.
- **Logic**: It establishes a requirement. `T: Clone` means "T must provide a `.clone()` method."

###2. The Double Colon (::)—The "Path" Operatoror

The double colon is a **Path Separator**. It is used to navigate the hierarchy of your code—crates, modules, and types. It’s strictly about **location**.

- **Node.js Mental Model**: `const Debug = require('std/fmt').Debug;`
- **Logic**: It tells the compiler exactly where to find the definition. `std::fmt::Debug` says: "Go to the `std` library, look inside the `fmt` module, and find the `Debug` trait."

The Default Trait 🏗️: How to use #\[derive(Default)\] to define a "standard starting state" for your enum or struct.

The `Default` trait 🏗️ is Rust's way of providing a "zeroed-out" or "baseline" state for a type. In Node.js, you might handle this by assigning initial values in a constructor or using a default object. In Rust, `#[derive(Default)]` automates this process.

### 🏛️ The Structural Logic

When you apply `#[derive(Default)]` to a **struct**, it recursively calls `Default::default()` for every field. If your struct contains a `String`, a `u32`, and a `Vec`, the default struct will have an empty string, the number `0`, and an empty vector.

For an **enum**, the logic is slightly different because the compiler needs to know which variant is the "starting" one.

### ⚙️ Setting the Baseline for IncrementStrategy

In your `enum`, you can use the `#[default]` attribute to nominate a specific variant as the baseline.

Rust

```markdown
#[derive(Debug, Clone, PartialEq, Eq, Default)]
pub enum IncrementStrategy {
    #[default]
    Patch, // This is now the "starting" state
    Minor,
    Major,
    Custom(String),
}
```

By adding this, you can now instantiate your strategy without naming a variant:

Rust

```markdown
// In TS: const strategy = IncrementStrategy.PATCH;

```

In TypeScript, if you want a `Shape` that can be either a `Circle` or a `Square`, you typically use a **Discriminated Union**. This requires a shared property (the "discriminant") so the compiler can tell them apart.

In Rust, this entire pattern is "flattened" into a single **enum**. Let's compare the architectural structure of both.

### 📐 The TypeScript Pattern

In TS, you define separate interfaces and then union them:

TypeScript

```markdown
interface Circle {
    kind: "circle"; // Discriminant
    radius: number;
}

interface Square {
    kind: "square"; // Discriminant
    side: number;
}

type Shape = Circle | Square;
```

### 🦀 The Rust Equivalent

In Rust, the variants *are* the "interfaces." You don't need a separate field like `kind` because the enum variant name itself acts as the discriminant.

Rust

```markdown
enum Shape {
    Circle { radius: f64 },
    Square { side: f64 },
}
```

### 🧠 Key Differences in Logic

1. **Atomicity**: In Rust, `Shape` is one single type. You cannot have a `Circle` variable that isn't part of the `Shape` enum (unless you define a separate `struct Circle`).
2. **Syntax Density**: Rust eliminates the boilerplate of defining `kind` properties.
3. **Pattern Matching**: While TS uses `switch (shape.kind)`, Rust uses a `match` statement that is deeply integrated with the language's safety features.

### 🛠️ The Power of Exhaustive Matching

Because the Rust compiler knows exactly what's inside a `Shape`, it forces you to handle every possibility when you use a `match` statement. In TypeScript, if you forget a `case` in a switch statement, it might just return `undefined` at runtime. In Rust, it won't even compile.

Rust

```markdown
fn area(shape: Shape) -> f64 {
    match shape {
        Shape::Circle { radius } => std::f64::consts::PI * radius * radius,
        Shape::Square { side } => side * side,
        // If we don't handle Shape::Triangle here, the compiler throws an error! 🛑
    }
}
```

This "Exhaustive Safety" is a major part of why Rust developers feel so confident refactoring code.

In the context of Rust enums, a **variant** is more than just a label; it represents a specific "branch" of a type that can carry distinct data.

In Type Theory and mathematics, Rust enums are known as **Sum Types** (specifically, **Tagged Unions**). This is where the rigour comes in. While a `struct` is a **Product Type** (containing `A` *and* `B`), a Sum Type contains `A` *or* `B`.

The term "variant" is used to describe these mutually exclusive states.

### 🧬 The Logical Structure of a Variant

Each variant in a Rust enum consists of two parts that the compiler manages with mathematical precision:

1. **The Discriminant (The Tag) 🏷️**: A small hidden integer that identifies *which* variant the data currently belongs to.
2. **The Payload (The Data) 📦**: The actual values stored within that specific variant.

| Aspect | TypeScript "Variant" (Conceptual) | Rust Variant (Formal) |
| --- | --- | --- |
| **Identity** | Usually a string literal (e.g., `kind: "circle"`) | A memory-efficient integer tag |
| **Logic** | Part of a union of separate types | A fundamental part of a single, unified type |
| **Enforcement** | Can be bypassed with `any` or casting | Strictly enforced by the compiler’s "exhaustiveness" check |

### 🔍 Connotation: Why it feels "Rigorous"

The term carries a connotation of **formal completeness**. When you define an enum, you are defining the *entire universe* of possible states for that variable.

In a language like Java or C++, you might use inheritance where a variable could be "any subclass of Shape." This is an **open set**—anyone can add a new subclass later. In Rust, an enum is a **closed set**. The compiler knows every possible variant at the moment it compiles the code. This "closed" nature is what allows for the mathematical certainty that you've handled every case.

In the Rust architectural model, `crate` is a **reserved keyword** that serves as a pointer to the **root of the current project**. It is not a custom module name, but rather an absolute path reference.

If you are coming from Node.js, think of `crate::` as the Rust equivalent of a **Root-Relative Alias** (like `@/` in many Vite or Webpack configurations) that always points to your `src/index.ts` or `src/main.ts`.

---

### 🏛️ The Hierarchy: Crates vs. Modules

To understand `use crate::`, you need to distinguish between the physical file and the logical "namespace" it belongs to:

1. **The Crate**: This is the entire compilation unit (your whole package). In your `Cargo.toml`, you define its name, but inside the code, you refer to it simply as `crate`.
2. **The Module**: These are the individual files or folders (`mod.rs`) inside your crate.

When you see `use crate::{...}`, you are telling the compiler:

> "Go to the **root** of this project, look through the public items exported there, and bring these specific types into my current file's scope."

---

### 🧠 The Mental Model: Absolute vs. Relative Paths

Rust handles imports using a filesystem-like path logic. There are three main ways to import something:

| Syntax | Mental Model | Description |
| --- | --- | --- |
| **`use crate::Type`** | `import { Type } from '@/root'` | **Absolute**: Starts from your project's root. |
| **`use super::Type`** | `import { Type } from '../'` | **Relative**: Moves up one level in the folder hierarchy. |
| **`use self::Type`** | `import { Type } from './'` | **Relative**: Looks inside the current module/file. |
| **`use some_lib::Type`** | `import { Type } from 'some-lib'` | **External**: Looks in your `dependencies` (node\_modules). |

---

### 🧩 Why use crate::? (Architectural Context)

As a software architect, you'll value `crate::` because it provides **refactoring stability**.

If you move a file from `src/logic/parser.rs` to `src/core/utils/parser.rs`:

- A **relative** import (`use super::super::SemanticVersion`) would break.
- An **absolute** import (`use crate::SemanticVersion`) remains valid because the path from the root to `SemanticVersion` hasn't changed.
