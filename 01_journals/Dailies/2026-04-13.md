## Mcpproxy healthcheck—2026-04-13

Context: Stabilising the local `mcpproxy` LaunchAgent that exposes upstream MCP servers via a single HTTP endpoint at `http://127.0.0.1:8000/mcp/`.

### Steps Taken

1. Reviewed `dot_config/mcpproxy/`—confirmed `mcp_proxy.json.tmpl` filters disabled servers before rendering, and that the README was pending a healthcheck section.
2. Identified portability risk in new `scripts/executable_mcpproxy-healthcheck.sh`—two `rg` (ripgrep) calls for JSON matching would fail in the LaunchAgent's restricted PATH.
3. Replaced `rg` with `grep` on lines 45 & 50 of the healthcheck script. No regex features needed—plain string match is sufficient and `grep` is always available.
4. Staged and committed three files together:
   - `dot_config/mcpproxy/README.md`—added "Health check helper" section
   - `scripts/executable_mcpproxy-healthcheck.sh`—new 3-phase healthcheck (listener → initialize → tools/list)
   - Commit: `feat(mcpproxy): add 3-phase healthcheck script`
5. Applied via chezmoi—`chezmoi apply` deployed the script to `~/scripts/mcpproxy-healthcheck.sh` with executable bit set (`-rwxr-xr-x`).
6. Ran healthcheck—all three phases passed:
   - TCP listener confirmed on `127.0.0.1:8000`
   - MCP `initialize` handshake returned `mcp-session-id`
   - `tools/list` confirmed `retrieve_tools` + `call_tool` present
   - Output: `OK: proxy is healthy and tool surface is ready`
7. Proved the MCP stack works end-to-end by writing this note via `obsidian-mcp-tools` through the proxy—no direct file writes used.

### Key Decision

Use `grep` not `rg` in scripts that run under LaunchAgent / restricted PATH environments. `rg` is a user-installed tool and not guaranteed to be on `$PATH` for daemon processes.
