### Verdict Model (From aCceptance cRiteria)

Precedence (highest first):

```
flowchart TD
  A[Finding from VulnerabilityReport CRD] --> B{VEX not_affected?}
  B -->|yes| S[suppressed]
  B -->|no| C{In CISA KEV?}
  C -->|yes| P0[P0]
  C -->|no| D{EPSS ≥ threshold?}
  D -->|yes| P1[P1]
  D -->|no| E{Defender: image not deployed?}
  E -->|yes| P3[P3]
  E -->|no| F{Kubescape: package not loaded?}
  F -->|no| G[P2 + CVSS tiebreak]
  F -->|yes| H{relevancy_trust trusted?}
  H -->|yes| P3
  H -->|no| G
```

New field: `relevancy_trust` —whether Kubescape's "not loaded" signal is trusted for that workload/runtime (OHDSI fat-jar Java was not discriminating in the FTFL-966 pilot; `workflows-api` Python was more useful).

Output metric (target):

```
trivy_vuln_verdict{cve, namespace, workload, container, verdict="P0|P1|P2|P3|suppressed"}
```

Plus a ranked VEX-candidate queue for P2 findings that survive automated filters.

### Recommended Approach: Extend the Exporter (Not a nEw ASPM)

The ticket explicitly asks to extend `trivy-epss-kev-exporter` or a sibling tool. That matches what's already in staging:

- ServiceMonitor + Alloy scrape of `trivy-system` proven
- Read-only RBAC on `vulnerabilityreports` + informer pattern proven
- Vendored build pipeline + security review process established (FTFL-947)

Option A (preferred): evolve `trivy-epss-kev-exporter` into a unified verdict exporter (rename optional later).

Option B: sibling deployment in the same pod pattern if you want to keep EPSS/KEV frozen while iterating on verdict logic—more Terraform/RBAC duplication, probably not worth it.

#### Phase 2—VEX Input

Two paths (pick based on Phase 0 clarification):
